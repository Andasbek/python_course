## 1. Что такое проект?

**Проект** (project) – работа, спланированная для достижения конкретного результата (продукта) в определённый срок. В программировании продукт – **работающая программа**.

Признаки проекта:
- есть **цель** (какую проблему решает, для кого);
- **срок** ограничен;
- **результат** конкретный (программа + документация);
- делится на **этапы**.

### Жизненный цикл программного проекта

| Этап | Что делается | Результат |
|---|---|---|
| Планирование | Выбор задачи, требования, список функций | ТЗ, план |
| Разработка 1 | Основная логика | Работающая минимальная версия (MVP) |
| Разработка 2 | Интерфейс (меню), сохранение данных | Полная версия |
| Тестирование | Поиск и исправление ошибок, оформление кода | Стабильная версия, README |
| Выпуск | Демонстрация, передача пользователям | Готовый продукт |

**Аналогия – строительство дома.** Сначала чертёж (план), затем фундамент и стены (основная логика), затем двери-окна и отделка (интерфейс), проверка (тестирование), в конце – сдача дома (защита). Дом, построенный без чертежа, может рухнуть!

## 2. Выбор задачи для проекта

Признаки хорошей задачи:

1. **Понятная цель** – ясно, кто и зачем будет пользоваться программой.
2. **Полезная или интересная** – программой можно пользоваться или в неё интересно играть.
3. **Выполнимая** – объём соответствует времени и имеющимся знаниям.
4. **Использует основные средства языка** – ветвление, циклы, список/словарь, свои функции, работу с файлом и `try...except`, стандартные модули.

### Виды проектов

| Вид | Примеры | Основные темы |
|---|---|---|
| Игра | «Угадай число+», «Виселица» (угадай слово), «Турнир камень-ножницы-бумага», текстовый квест | `random`, `while`, строки, файл (рекорд) |
| Учебный тренажёр | Таблица умножения, английские слова, викторина по истории | Словарь, `random`, вопросы из файла, `time` |
| Полезный инструмент | Дневник домашних заданий, учёт карманных денег, каталог библиотеки | Словарь/список, файл, `datetime` |
| Калькулятор | Геометрический калькулятор, ИМТ, обмен валют, анализ оценок | `math`, функции, `try...except` |
| Графический | Интерактивный рисунок в Turtle, «Звёздное небо», графики | `turtle`, циклы, `random`, `math` |

> **Правило.** Не бери слишком большой проект! «Игра как Minecraft» в короткий срок не уложится. «Текстовая игра-лабиринт, 5 комнат, сундук и рекорд» – как раз такой объём.

## 3. MVP – сначала самое важное

**MVP** (Minimum Viable Product – минимально жизнеспособный продукт) – самая простая, но **работающая** версия проекта. Сначала делаем MVP, а затем, если останется время, – дополнительные возможности.

**Пример: «Викторина о Казахстане».**

| Уровень | Возможности |
|---|---|
| **MVP (обязательно)** | 10 вопросов в словаре; задаёт по очереди; проверяет ответ; в конце выводит баллы |
| **Хорошая версия** | Вопросы в случайном порядке; вопросы читаются из файла; результат сохраняется в файл; меню |
| **Отличная версия** | Уровни сложности; игра на время; таблица ТОП-5 рекордов; режим добавления новых вопросов |

Такой подход даёт гарантию: даже если времени не хватит, у тебя будет работающая программа.

## 4. Техническое задание (ТЗ)

**Техническое задание** (ТЗ, technical specification) – документ, описывающий, **что должна делать** программа. В настоящих IT-компаниях любой проект начинается с него.

Структура ТЗ:
1. **Название проекта.**
2. **Цель** – какую проблему решает, для кого (1–2 предложения).
3. **Функциональные требования** – что умеет программа (список: «Программа делает ...»).
4. **Входные и выходные данные** – что вводит пользователь, что видит, какие файлы используются.
5. **Используемые технологии** – какие модули, структуры.
6. **Ограничения** – что **не входит** (например: «графического окна нет, только консоль»).

**Пример ТЗ (краткий):**

```text
Название: «Викторина о Казахстане»
Цель: проверить в игровой форме знания учеников 5–7 классов о Казахстане.
Функциональные требования:
  1. Программа показывает главное меню: Играть / Рекорды / Выход.
  2. В игре задаются 10 вопросов в случайном порядке.
  3. Ответ проверяется без учёта регистра букв.
  4. За каждый правильный ответ 1 балл; в конце выводятся результат и оценка.
  5. Результат (имя, баллы, дата) сохраняется в файл results.txt.
  6. В меню рекордов показываются ТОП-5 результатов.
Вход: имя игрока, ответы; questions.txt (вопрос|ответ).
Выход: баллы на экране, файл results.txt.
Технологии: функции, словарь, список, random, datetime, файлы, try...except.
Ограничения: только консольный интерфейс; один игрок.
```

## 5. Декомпозиция: разбиение проекта на части

**Декомпозиция** – разбиение большой задачи на маленькие понятные части. В программе каждая часть – это обычно одна **функция**.

Для викторины:

```text
Викторина о Казахстане
├── load_questions()   – чтение вопросов из файла
├── ask_question()     – задать один вопрос и проверить ответ
├── play()             – вся игра: перемешать вопросы, подсчитать баллы
├── save_result()      – записать результат в файл
├── show_records()     – ТОП-5 результатов
└── main()             – главное меню
```

Для каждой функции определи: **что принимает** (параметры) и **что возвращает** (`return`).

| Функция | Параметры | Возвращает |
|---|---|---|
| `load_questions(file_name)` | имя файла | словарь `{вопрос: ответ}` |
| `ask_question(question, answer)` | вопрос, правильный ответ | `True` / `False` |
| `play(questions)` | словарь вопросов | баллы (int) |
| `save_result(name, score)` | имя, баллы | – |
| `show_records()` | – | – |

## 6. Как хранить данные?

Важно выбрать структуру данных на этапе планирования:

| Данные | Структура | Пример |
|---|---|---|
| Одно значение | переменная | `score = 0` |
| Однородная последовательность | список | `words = ["яблоко", "гора"]` |
| Неизменяемая группа | кортеж | `size = (800, 600)` |
| Соответствие имя → значение | словарь | `{"Астана": "астана"}` |
| Набор без повторов | множество | `used = {"гора", "река"}` |
| Должно сохраниться после программы | файл | `results.txt` |

## 7. Описание алгоритма: псевдокод и блок-схема

Основной алгоритм проекта можно изобразить блок-схемой или описать коротким **псевдокодом** (алгоритм, записанный простым языком):

```text
НАЧАЛО
  прочитать вопросы из файла
  ПОВТОРЯТЬ:
    показать меню
    прочитать выбор
    ЕСЛИ выбор = 1: играть, сохранить результат
    ЕСЛИ выбор = 2: показать рекорды
    ЕСЛИ выбор = 0: выход
КОНЕЦ
```

Потом «перевести» это на Python очень легко.

## 8. План работ и риски

План – это список **конкретных** задач. «Сделать проект» – не план. «Написать и проверить функции `load_questions()` и `ask_question()`» – план. Каждая задача должна быть небольшой и проверяемой.

**Риски** (что может пойти не так) и их решение:
- не хватает времени → сначала доделай MVP, дополнительные возможности – потом;
- не получается какая-то часть → временно замени её заглушкой (`pass` или упрощённая версия) и переходи к другой части;
- пропали файлы → регулярно делай резервные копии (облако, флешка) с датой в имени (`quiz_2027-05-03.py`) или используй систему контроля версий Git.

## Частые ошибки (при планировании)

**1. Слишком большая идея.** «Онлайн-игра по сети» требует знаний сетевого программирования, баз данных и графики. Уменьши идею до MVP.

**2. Слишком маленькая идея.** «Калькулятор, складывающий два числа» – слишком мало для проекта: в нём нет ни структур данных, ни функций, ни работы с файлами. Добавь возможности (история, файл, меню, проверка).

**3. Писать код сразу без плана.** В итоге – 300 строк «запутанного» кода, который невозможно исправить. Сначала список функций!

**4. Делать всё в одной функции.** Проведи декомпозицию: одна функция – одна задача.

**5. «Зашивать» данные в код.** Если вопросы, слова, товары хранятся в файле, программу можно пополнять, не изменяя её.

## Основные понятия

| Понятие | Пояснение |
|---|---|
| Проект | Работа с ограниченным сроком, направленная на конкретный результат |
| Техническое задание (ТЗ) | Документ с требованиями к программе |
| MVP | Минимальная, но работающая версия |
| Декомпозиция | Разбиение задачи на маленькие части |
| Псевдокод | Запись алгоритма простым языком |
| Функциональное требование | Описание вида «Программа умеет ...» |
| Риск | Ситуация, которая может помешать проекту |

## Примечание

- Структура типичного небольшого Python-проекта: `main.py` (точка входа), модули с функциями (`quiz.py`, `storage.py`), папка `data/` с файлами данных и `README.md` с описанием.
- Запуск программы принято оформлять через функцию `main()` и блок `if __name__ == "__main__": main()` – тогда модули проекта можно импортировать без автоматического запуска игры.
- Имена файлов и функций по PEP 8 – строчными буквами через подчёркивание (`load_questions`, `save_result.py`); не называй файлы проекта именами стандартных модулей (`random.py`, `time.py`).
- Для сложных структур данных (список словарей) формат JSON (`json.dump`/`json.load`) надёжнее самодельного формата с разделителями.
- Для истории изменений и резервных копий в профессиональной разработке используют Git: каждый рабочий шаг сохраняется коммитом, к любой версии можно вернуться.
- Полезно: [PEP 8 – Style Guide](https://peps.python.org/pep-0008/), [Python Tutorial](https://docs.python.org/3/tutorial/index.html).
