## 1. Почему команда?

Настоящие игры создаёт не один человек, а команда. Например, и казахстанские игровые студии, и мировые студии объединяют в работе программистов, художников, звукорежиссёров, тестировщиков.

**Аналогия:** командный проект похож на футбольную команду. Если все будут вратарями — команда проиграет; если все будут нападающими — тоже проиграет. У каждого своё место, но цель — общая.

Польза работы в команде:
- **скорость** — несколько человек одновременно занимаются разными частями;
- **качество** — каждый сосредоточен на той области, которую хорошо знает;
- **обучение друг у друга** — совместный просмотр кода (code review) повышает знания;
- **подготовка к реальной жизни** — в IT-сфере работа всегда проходит в команде.

Есть и трудности: разногласия, когда кто-то один «тащит весь груз», несовместимость кода разных участников. Их мы решаем с помощью **планирования** и **правил**.

## 2. Роли в команде

В небольшой команде 3–4 человека, поэтому один участник может выполнять одну или две роли.

| Роль | Основная обязанность | Результат (артефакт) |
|---|---|---|
| **Тимлид** (руководитель команды) | Следит за планом, распределяет задачи, проводит встречи, управляет репозиторием GitHub | Kanban-доска, репозиторий, план |
| **Программист (код)** | Пишет логику игры: игровой цикл, персонаж, враги, столкновения, очки | Модули `.py` |
| **Графический дизайнер** | Спрайты, фон, элементы интерфейса, цветовая палитра | Изображения в `assets/images/` |
| **Звуковой дизайнер** | Находит/создаёт звуковые эффекты и фоновую музыку, проверяет лицензию | Файлы в `assets/sounds/` |
| **Тестировщик (QA)** | Играет в игру, находит ошибки и записывает их в список | Список ошибок (bug list) |

> **Важно:** участник, отвечающий за графику и звук, тоже работает **с кодом**! Например, художник пишет функцию `load_image()`, звукорежиссёр — модуль `sound.py`. Каждый участник добавляет в проект хотя бы один модуль кода.

### Как распределить роли?

1. Каждый участник называет свою сильную сторону («Мне нравится рисовать», «Я хорошо понимаю классы»).
2. Тимлида команда выбирает сама (обычно это тот, кому нравится организовывать).
3. Заполняем матрицу ролей (упрощённый вариант RACI):

| Задача | Алия (тимлид) | Нурлан (код) | Дана (графика) | Ерасыл (звук, QA) |
|---|---|---|---|---|
| Игровой цикл, `main.py` | помогает | **ответственный** | — | проверяет |
| Класс игрока | проверяет | **ответственный** | даёт спрайт | тестирует |
| Фон, спрайты | — | — | **ответственная** | — |
| Звуки | — | добавляет | — | **ответственный** |
| Экран меню | **ответственная** | помогает | дизайн | тестирует |
| README, защита | **ответственная** | пишет раздел | скриншот | пишет раздел |

У каждой задачи должен быть **только один ответственный**. «Мы все ответственны» — значит, никто не ответственен.

## 3. Правила работы команды

Команда в самом начале записывает «соглашение команды»:
- все решения обсуждаются, последнее слово — за тимлидом (но можно проголосовать);
- критикуем код, а не человека: «Эта функция получилась слишком длинной» — правильно; «Ты плохо пишешь» — неправильно;
- если не можешь выполнить свою задачу — сразу скажи, просить помощи не стыдно;
- не изменяем чужой файл без разрешения (эту проблему решают ветки Git);
- каждый рабочий день начинается с короткого (до 3 минут) **стендапа**: «Что я сделал вчера? Что сделаю сегодня? Что мне мешает?».

## 4. Выбор идеи игры

Идея должна быть **выполнимой** за отведённое время (обычно это несколько дней работы небольшой команды). Поэтому:

| Хорошая идея | Слишком большая идея |
|---|---|
| 2D-платформер, 3 уровня | 3D RPG с открытым миром |
| «Космический шутер» (вид сверху) | Сетевая MMO |
| Игра в духе «Змейки», «Тетриса», со своей особенностью | Сюжетная игра с 50 персонажами |
| «Сбор яблок» — ловить падающие предметы корзиной | Симулятор автомобиля с физическим движком |

### Техника мозгового штурма

1. Каждый участник пишет 2–3 идеи на стикерах (не критикуем!).
2. Идеи вешают на доску, похожие объединяют.
3. У каждого участника 2 голоса — ставит точки.
4. Идею, набравшую больше всего голосов, проверяют на «выполнимость».

### Придаём игре «казахстанский колорит»

Игра станет гораздо интереснее, если у неё будет своё лицо: степь, лошади, горы Алатау, беркуты, тумар, фон с казахским орнаментом, мелодия домбры и т.д. Пример: «Қыран» — беркут летит над горами и уворачивается от препятствий.

## 5. Документ дизайна игры (GDD)

**GDD (Game Design Document)** — «паспорт» игры. В нём записано, о чём игра, как в неё играть, какие ресурсы нужны. Наш GDD — не больше одной страницы.

Разделы GDD:
1. **Название и жанр** — «Қыран», аркада/раннер (runner).
2. **Идея одним предложением (elevator pitch)** — «Управляй беркутом, пролети невредимым над горами и собери золотые тумары».
3. **Цель** — ради чего играет игрок? (набрать очки, пройти уровень).
4. **Управление** — какие клавиши? (`←` `→` `↑` `↓`, `Space`, `Esc` — пауза).
5. **Игровая механика** — персонаж, враги, бонусы, жизни, уровни.
6. **Условие победы/поражения** — закончились 3 жизни — Game Over; 1000 очков — следующий уровень.
7. **Экраны** — главное меню, игра, пауза, Game Over.
8. **Список ресурсов** — изображения, звуки, шрифты.
9. **MVP и дополнения**.

## 6. MVP — минимально работающая версия

**MVP (Minimum Viable Product)** — самая простая, но **играбельная** версия игры. Сначала делаем MVP, остальное добавляем, если останется время.

**Аналогия:** если печёшь торт, сначала выпекаешь бисквит (MVP). Крем, ягоды, надпись — потом. Если без бисквита сразу делать крем, торта не получится.

| MVP (обязательно) | Дополнительно (если будет время) |
|---|---|
| Игрок двигается с клавиатуры | Анимация игрока |
| Появляются враги | Несколько видов врагов |
| Столкновение → жизни уменьшаются | Бонусы-сердечки |
| Счётчик очков | Таблица рекордов (сохранение в файл) |
| Экран Game Over | Уровни, враг-босс |
| — | Настройки звука |

Для расстановки приоритетов удобен метод **MoSCoW**: Must (обязательно), Should (нужно), Could (было бы хорошо), Won't (в этот раз — нет).

## 7. Распределение задач и Kanban-доска

Большая работа состоит из маленьких задач. Одна задача не должна занимать больше одного рабочего сеанса (30–60 минут).

Плохая задача: «Сделай игру».
Хорошие задачи: «Напиши класс Player: движение влево-вправо, не выходить за пределы экрана», «Нарисуй фон 800×600», «Найди звук удара (с открытой лицензией)».

**Kanban-доска** — распределяем задачи по колонкам:

```text
| Нужно сделать (To Do) | В работе (In Progress) | На проверке (Review) | Готово (Done) |
|-----------------------|------------------------|----------------------|---------------|
| Класс врагов          | Класс Player (Нурлан)  | Фон (Дана)           | Репозиторий   |
| Экран Game Over       | Меню (Алия)            |                      | GDD           |
| Звук удара            |                        |                      |               |
```

Доску можно вести на бумаге (со стикерами), в Trello или в **GitHub Projects**. На GitHub каждую задачу можно открыть как **Issue** и назначить (assign) ответственному.

## 8. Файловая структура проекта

Если четыре человека одновременно редактируют один файл `main.py` — будет путаница. Поэтому код разбиваем на **модули**; у каждого модуля один владелец.

```text
qyran_game/
├── main.py          # игровой цикл, переключение экранов (тимлид)
├── settings.py      # константы: размер, цвет, FPS (читают все)
├── player.py        # класс Player (программист)
├── enemies.py       # класс Enemy (программист)
├── assets.py        # загрузка изображений и звуков (графика/звук)
├── ui.py            # меню, очки, текст (тимлид)
├── assets/
│   ├── images/
│   └── sounds/
├── README.md
└── .gitignore
```

Общие константы находятся в одном месте, тогда все используют одинаковые значения:

```python
# settings.py — общие настройки для всех модулей
WIDTH = 800
HEIGHT = 600
FPS = 60
TITLE = "Қыран"

WHITE = (255, 255, 255)
BLACK = (0, 0, 0)
SKY_BLUE = (135, 206, 235)
GOLD = (255, 215, 0)

PLAYER_SPEED = 5
START_LIVES = 3
```

Другой модуль использует их так:

```python
# player.py
import pygame
from settings import WIDTH, HEIGHT, PLAYER_SPEED


class Player(pygame.sprite.Sprite):
    """Игрок — беркут. Управляется клавишами-стрелками."""

    def __init__(self):
        super().__init__()
        self.image = pygame.Surface((50, 40))
        self.image.fill((139, 69, 19))  # временный коричневый прямоугольник
        self.rect = self.image.get_rect(center=(100, HEIGHT // 2))

    def update(self):
        keys = pygame.key.get_pressed()
        if keys[pygame.K_UP]:
            self.rect.y -= PLAYER_SPEED
        if keys[pygame.K_DOWN]:
            self.rect.y += PLAYER_SPEED
        # не выходить за пределы экрана
        self.rect.top = max(self.rect.top, 0)
        self.rect.bottom = min(self.rect.bottom, HEIGHT)
```

> **«Временный прямоугольник» (placeholder)** — программист не ждёт художника. Сначала он работает с цветным прямоугольником, а когда изображение готово, меняется только строка `self.image`.

### «Договорённость» между модулями (интерфейс)

Заранее договариваемся, что каждый модуль даёт другим. Например, графический дизайнер и программист договариваются о такой функции:

```python
# assets.py
import os
import pygame

ASSETS_DIR = os.path.join(os.path.dirname(__file__), "assets")


def load_image(name, size=None):
    """Загружает изображение из assets/images, при необходимости меняет его размер."""
    path = os.path.join(ASSETS_DIR, "images", name)
    image = pygame.image.load(path).convert_alpha()
    if size is not None:
        image = pygame.transform.scale(image, size)
    return image
```

Программисту достаточно вызвать `load_image("eagle.png", (50, 40))`, ему не обязательно знать, что внутри функции.

## 9. Лицензия ресурсов

Брать из интернета любое изображение или песню **нельзя** — это нарушение авторского права. Ресурсы с открытой лицензией:
- **Kenney.nl** — бесплатная игровая графика (CC0);
- **OpenGameArt.org** — графика и звук (нужно проверять лицензию);
- **Freesound.org** — звуковые эффекты;
- изображение, нарисованное самостоятельно (Piskel, GIMP, Krita), или звук, записанный самостоятельно, — лучший вариант!

В файле README записываем, откуда взят каждый ресурс.

## Частые ошибки

**1. Слишком большая идея.** Команда решает сделать игру «как Minecraft», и к сроку сдачи ничего не готово.
→ Правильно: сначала MVP, потом дополнения.

**2. Все пишут в одном файле.** Четыре человека меняют один `main.py`, потом изменения затирают друг друга.
→ Правильно: разбиение на модули, у каждого файла есть владелец.

**3. Константы в разных файлах разные.**

```python
# в player.py
WIDTH = 800
# в enemies.py
WIDTH = 1024  # ошибка: размеры экрана не совпадают!
```

→ Правильно: все константы только в `settings.py`, остальные получают их через `from settings import WIDTH`.

**4. Модуль запускает игру при импорте.** Если кто-то допишет в конец `player.py` игровой цикл для теста, то при `import player` откроется окно.

```python
# Правильно: выполнять тестовый код только при прямом запуске файла
if __name__ == "__main__":
    print("Модуль player.py проверяется отдельно")
```

**5. Участник без роли.** Участник, который говорит «Я просто помогаю», в итоге ничего не делает.
→ Правильно: у каждого участника на Kanban-доске должно быть минимум 2–3 задачи.

## Основные понятия

| Понятие | Объяснение |
|---|---|
| Тимлид (team lead) | Руководитель, который организует команду и следит за планом |
| Роль | Зона ответственности человека в команде |
| GDD | Документ дизайна игры — краткое описание игры |
| MVP | Минимально работающая версия — самая простая играбельная игра |
| MoSCoW | Метод деления приоритетов на Must / Should / Could / Won't |
| Kanban | Доска, распределяющая задачи по колонкам «Нужно сделать → В работе → Готово» |
| Стендап | Короткая ежедневная встреча: что сделал, что сделаю, что мешает |
| Placeholder | Временное изображение/звук, используемое, пока не готов настоящий ресурс |
| Лицензия | Правило, определяющее право на использование ресурса (например, CC0) |

## Примечание

- **`if __name__ == "__main__":`** — обязательная защита в каждом модуле, который можно запускать отдельно: код под этим условием не выполняется при `import`.
- **Имена модулей** по PEP 8 пишутся строчными буквами, слова разделяются `_` (`player.py`, `game_over.py`); не называйте модуль так же, как библиотеку (`pygame.py`, `random.py`) — иначе `import` найдёт ваш файл вместо библиотеки.
- **Циклический импорт** (`player.py` импортирует `enemies.py`, а `enemies.py` — `player.py`) приводит к `ImportError`. Общие данные выносите в отдельный модуль (`settings.py`), который сам ничего из проекта не импортирует.
- **Пути к ресурсам** стройте относительно файла модуля (`os.path.dirname(__file__)` или `pathlib.Path(__file__).parent`), а не относительно текущей папки — тогда игра запустится из любого каталога.
- `convert_alpha()` и `convert()` работают только после `pygame.display.set_mode()`; поэтому изображения загружают после создания окна.
- Зависимости проекта фиксируйте в `requirements.txt` (например, `pygame==2.6.1`), чтобы у всех участников была одна версия библиотеки. Документация: https://www.pygame.org/docs/ и https://docs.python.org/3/tutorial/modules.html
