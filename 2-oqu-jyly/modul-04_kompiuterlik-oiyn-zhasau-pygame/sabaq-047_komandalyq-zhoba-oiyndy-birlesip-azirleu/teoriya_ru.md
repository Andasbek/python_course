## 1. Командный репозиторий: Collaborator и clone

Тимлид создаёт репозиторий на GitHub и приглашает остальных:
**Settings → Collaborators → Add people** → логин товарища по команде. Товарищ принимает приглашение, пришедшее на почту.

Каждый участник копирует репозиторий на свой компьютер:

```bash
git clone https://github.com/aliya-team/qyran-game.git
cd qyran-game
git config user.name "Nurlan Seitov"
git config user.email "nurlan@example.com"
```

`git clone` создаёт полную копию репозитория вместе со всей его историей и автоматически настраивает удалённую (remote) связь с именем `origin`.

## 2. Главная проблема командной работы

Представьте: Нурлан и Дана одновременно изменили `main.py`. Нурлан первым сделал `push`. Когда Дана делает `push`, Git его не принимает:

```text
! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/aliya-team/qyran-game.git'
hint: Updates were rejected because the remote contains work that you do not have locally.
```

Git говорит: «На сервере есть новые изменения, которых у тебя нет. Сначала получи их (`pull`)». Это не ошибка, а **защита**: Git не стирает молча чужую работу.

**Золотое правило:** перед началом работы — `git pull`; по окончании работы — `commit`, `pull`, затем `push`.

## 3. Ветки (branch)

**Ветка** — параллельная версия проекта. Основная ветка `main` всегда хранит **работающую** игру. Каждый участник делает новую возможность в своей ветке и, когда она готова, добавляет её в `main`.

**Аналогия:** `main` — чистовик. Каждый участник сначала пишет в свой черновик (ветку), и только после проверки изменения переносятся в чистовик.

```text
main:      A───B───────────F───G
                \         /   /
feature/player   C───D───┘   /
                  \         /
feature/sound      E───────┘
```

### Команды для работы с ветками

| Команда | Что делает |
|---|---|
| `git branch` | Показывает все локальные ветки (`*` — текущая) |
| `git branch feature/player` | Создаёт новую ветку |
| `git switch feature/player` | Переключается на ветку (старый способ: `git checkout`) |
| `git switch -c feature/player` | Создаёт и сразу переключается |
| `git merge feature/player` | Объединяет указанную ветку с текущей |
| `git branch -d feature/player` | Удаляет объединённую ветку |
| `git push -u origin feature/player` | Впервые отправляет ветку на GitHub |

Соглашение об именах веток: `feature/...` — новая возможность, `fix/...` — исправление ошибки, `assets/...` — ресурсы.

### Порядок работы с веткой-возможностью (feature branch)

```bash
# 1. Обновить main
git switch main
git pull

# 2. Создать ветку для своей задачи
git switch -c feature/enemies

# 3. Работать, часто делать коммиты
git add enemies.py
git commit -m "Класс Enemy: движение справа налево"

# 4. Отправить ветку на GitHub
git push -u origin feature/enemies

# 5. Открыть Pull Request на GitHub, товарищ проверяет, нажимается Merge

# 6. Вернуться в main и обновить
git switch main
git pull
git branch -d feature/enemies
```

## 4. Pull Request и проверка кода (code review)

**Pull Request (PR)** — запрос «Прошу добавить мою ветку в `main`». После отправки ветки на GitHub появляется кнопка **Compare & pull request**.

Что пишется в PR:
- **название:** «Добавлен класс врагов»;
- **описание:** что изменилось, как проверить, к какой задаче Kanban относится (например, `Closes #4` — Issue №4 закроется автоматически).

Товарищ по команде (например, тимлид) читает код в разделе **Files changed**, оставляет комментарии к строкам и в конце ставит **Approve** (одобрить) или **Request changes** (запросить исправления).

### Чек-лист code review

- [ ] Игра запускается, ошибок нет
- [ ] Код написан по PEP 8, имена понятные
- [ ] У классов и функций есть docstring
- [ ] Константы берутся из `settings.py`
- [ ] Файлы других людей не изменены без необходимости
- [ ] Нет лишних файлов (`__pycache__`, `.venv`)

Комментарии пишем вежливо: «Может, вынесем здесь `speed` в `settings.py`?» — гораздо лучше, чем «Это ошибка, перепиши».

## 5. Конфликт слияния (merge conflict)

Если два человека по-разному изменили **одну и ту же строку одного файла**, Git не знает, какой вариант выбрать, — возникает **конфликт**.

Пример: в `settings.py` Нурлан изменил `FPS = 60` на `FPS = 30`, а Дана — на `FPS = 120`. Когда Дана делает `git pull` или `git merge`:

```text
Auto-merging settings.py
CONFLICT (content): Merge conflict in settings.py
Automatic merge failed; fix conflicts and then commit the result.
```

Внутри файла Git ставит метки:

```text
WIDTH = 800
HEIGHT = 600
<<<<<<< HEAD
FPS = 120
=======
FPS = 30
>>>>>>> main
TITLE = "Қыран"
```

- между `<<<<<<< HEAD` и `=======` — **твоя** версия;
- между `=======` и `>>>>>>>` — **пришедшая** версия.

### Шаги разрешения конфликта

1. Открыть файл (VS Code подсвечивает конфликт цветом и предлагает кнопки «Accept Current / Accept Incoming / Accept Both»).
2. **Договориться** с товарищем: какое значение правильное?
3. **Полностью удалить** метки (`<<<<<<<`, `=======`, `>>>>>>>`) и оставить правильный код:

```python
WIDTH = 800
HEIGHT = 600
FPS = 60  # согласовано с командой
TITLE = "Қыран"
```

4. Запустить игру и проверить.
5. Сделать коммит:

```bash
git add settings.py
git commit -m "Разрешён конфликт FPS в settings.py"
git push
```

### Как уменьшить количество конфликтов?

- у каждого файла один владелец (проект разбит на модули);
- часто делаем `pull` — объединять легко, пока изменений мало;
- маленькие PR: один PR — одна задача;
- общие файлы (`settings.py`, `main.py`) изменяем только по договорённости.

## 6. Хорошее сообщение коммита

Сообщение коммита — это письмо товарищам по команде. Прочитав его, нужно понять, что изменилось.

| Плохо | Хорошо |
|---|---|
| `update` | `Player: добавлена граница, чтобы не выходить за экран` |
| `asdf` | `Добавлен звук удара (hit.wav) и его воспроизведение` |
| `исправил` | `Fix: исправлена ошибка, из-за которой очки не обнулялись после Game Over` |
| `много изменений` | (в одном коммите — только одно осмысленное изменение) |

Правило: сообщение говорит, **что сделано**, не длиннее 50–70 символов, один коммит — одна мысль.

## 7. `.gitignore` — что не отправляем в репозиторий

Некоторые файлы появляются на компьютере автоматически, делиться ими не нужно (наоборот, они вызывают конфликты):

```text
# .gitignore
__pycache__/
*.pyc
.venv/
venv/
.vscode/
.idea/
.DS_Store
Thumbs.db
highscore.txt
```

`highscore.txt` — личный рекорд каждого игрока, его тоже не отправляем в репозиторий.

## 8. Полезные команды для просмотра

```bash
git status                     # что изменилось, в какой я ветке
git log --oneline --graph --all # история веток в виде схемы
git diff                       # изменения, для которых ещё не сделан add
git fetch                      # получить новости с сервера (без слияния)
git restore player.py          # отменить несохранённые изменения в файле
```

Пример вывода `git log --oneline --graph --all`:

```text
*   7c1e2a9 (HEAD -> main, origin/main) Merge pull request #3 from aliya-team/feature/enemies
|\
| * 51d0b3f Enemy: появление на случайной высоте
| * 2a9f4c1 Класс Enemy: движение справа налево
* | e8b7d20 Класс Player и управление
|/
* 0f3a6b2 Каркас проекта: settings.py, main.py
```

## 9. Сборка модулей в одну игру

После того как каждый участник написал свой модуль, `main.py` их объединяет. Пример:

```python
# enemies.py — модуль программиста
import random
import pygame

WIDTH, HEIGHT = 800, 600  # в проекте: from settings import WIDTH, HEIGHT


class Enemy(pygame.sprite.Sprite):
    """Препятствие, летящее справа налево (горная вершина или облако)."""

    def __init__(self, speed=4):
        super().__init__()
        self.image = pygame.Surface((40, 40))
        self.image.fill((90, 90, 90))
        y = random.randint(20, HEIGHT - 60)
        self.rect = self.image.get_rect(topleft=(WIDTH, y))
        self.speed = speed

    def update(self):
        self.rect.x -= self.speed
        if self.rect.right < 0:
            self.kill()  # если вышел за экран — удаляется из группы
```

```python
# часть main.py, отвечающая за объединение (фрагмент)
import pygame
from player import Player
from enemies import Enemy

SPAWN_ENEMY = pygame.USEREVENT + 1
pygame.time.set_timer(SPAWN_ENEMY, 1000)  # враг каждую секунду

all_sprites = pygame.sprite.Group()
enemies = pygame.sprite.Group()
player = Player()
all_sprites.add(player)
```

Модули связаны друг с другом только через **имена классов и методы** — поэтому их могут писать разные люди в разных ветках.

## Частые ошибки

**1. Push напрямую в `main`.** Незаконченный код попадает в `main`, и игра ломается у всей команды.
→ Правильно: всегда работать в ветке `feature/...` и объединять через PR.

**2. Коммит без удаления меток конфликта.**

```text
<<<<<<< HEAD
FPS = 120
=======
FPS = 30
>>>>>>> main
```

Python не может прочитать эти строки → `SyntaxError`. Правильно: полностью удалить метки, оставить одно значение, запустить игру и проверить.

**3. Начало работы без `pull`.** Долгая работа на старой версии, а в конце — большой конфликт. Правильно: перед началом работы — `git switch main` и `git pull`.

**4. Отправка `__pycache__` и `.venv` в репозиторий.** Правильно: создать `.gitignore` в самом начале проекта. Если уже отправил:

```bash
git rm -r --cached __pycache__
git commit -m "__pycache__ удалён из репозитория"
```

**5. Не заметить, что находишься в другой ветке.** В первой строке `git status` всегда написана текущая ветка: `On branch feature/player`. Проверяй перед коммитом!

**6. Циклический импорт.** `player.py` → `import main`, `main.py` → `import player` — если они импортируют друг друга, возникает `ImportError`. Правильно: модули импортируют только `settings.py`, а объединяет их только `main.py`.

## Основные понятия

| Понятие | Объяснение |
|---|---|
| Collaborator | Участник, которому дано право записи в репозиторий |
| `git clone` | Создание полной копии удалённого репозитория |
| Ветка (branch) | Параллельная линия развития проекта |
| `main` | Основная ветка, которая всегда работает |
| Merge | Объединение изменений одной ветки с другой |
| Pull Request (PR) | Запрос на GitHub на объединение ветки |
| Code review | Чтение и проверка кода товарища по команде |
| Merge conflict | Конфликт, возникающий, когда два изменения затрагивают одну строку |
| `origin` | Имя по умолчанию для удалённого репозитория (на GitHub) |
| `.gitignore` | Список файлов, которые Git не отслеживает |

## Примечание

- `git switch` и `git restore` появились в Git 2.23 вместо перегруженной команды `git checkout`; в старых инструкциях встречается `git checkout -b feature/x` — это то же самое, что `git switch -c feature/x`.
- `git pull` = `git fetch` + `git merge`. Вариант `git pull --rebase` переносит ваши коммиты поверх свежих и делает историю линейной, но его нельзя применять к уже опубликованным общим веткам.
- Python-файлы с неразрешённым конфликтом не запускаются (`SyntaxError`), а вот в `.json`, `.txt` и `.md` метки `<<<<<<<` могут остаться незамеченными — перед коммитом ищите их командой `git diff --check` или `git grep "<<<<<<<"`.
- `.gitignore` не действует на файлы, которые уже отслеживаются; их нужно убрать из индекса командой `git rm --cached`.
- Чтобы у всех участников было одинаковое окружение, в репозиторий кладут `requirements.txt` (создаётся `pip freeze > requirements.txt`), а саму папку `.venv` — никогда.
- Официальная документация: https://git-scm.com/doc и раздел о модулях Python https://docs.python.org/3/tutorial/modules.html
