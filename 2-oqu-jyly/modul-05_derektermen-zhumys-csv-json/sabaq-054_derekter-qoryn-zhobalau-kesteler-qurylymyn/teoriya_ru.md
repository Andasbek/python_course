## 1. Почему сначала проектируем?

Прежде чем построить дом, архитектор создаёт **проект (чертёж)**: сколько комнат, где двери, как комнаты связаны. После заливки фундамента передвинуть комнату очень дорого.

С базой данных так же: после того как в таблице накопились тысячи записей, менять структуру трудно и опасно. Поэтому **до написания кода** проектируем модель данных на бумаге (или в диаграмме).

Признаки плохо спроектированной БД:
- данные **повторяются** (телефон одного руководителя кружка в 300 местах);
- **аномалия обновления** — изменили в одном месте, забыли в другом, возникло противоречие;
- **аномалия добавления** — если в кружке пока нет учеников, кружок добавить невозможно;
- **аномалия удаления** — если удалить единственного ученика, пропадут и сведения о кружке.

## 2. Этапы проектирования

```text
1. Анализ предметной области  →  «Что должна делать система? На какие вопросы отвечать?»
2. Поиск сущностей (entity)   →  существительные: ученик, кружок, руководитель, кабинет
3. Определение атрибутов      →  характеристики каждой сущности: имя, дата рождения, телефон
4. Определение связей         →  глаголы: ученик «посещает» кружок
5. Преобразование в таблицы   →  PK, FK, типы, ограничения
6. Проверка (нормализация)    →  нет ли повторов? Отвечает ли на все вопросы?
```

### Этап 1. Предметная область: «Центр детского творчества»

Требования (слова заказчика):

> «У нас есть несколько кружков (Python, Робототехника, 3D-моделирование). Каждый кружок ведёт один руководитель, один руководитель может вести несколько кружков. Ученик может записаться в несколько кружков. Мы хотим знать, в какой день ученик записался. У каждого кружка есть кабинет. Нужно хранить телефоны родителей.»

### Этап 2. Поиск сущностей

**Сущность (entity)** — реальный или абстрактный объект, данные о котором хранятся. Ищем в тексте **существительные**: кружок, руководитель, ученик, кабинет, родитель, запись.

Каждой сущности — одна таблица: `clubs`, `teachers`, `students`, `rooms` ...

### Этап 3. Атрибуты

| Сущность | Атрибуты |
|---|---|
| Ученик | имя, фамилия, дата рождения, школа, телефон родителя |
| Руководитель кружка | ФИО, телефон, email, специальность |
| Кружок | название, направление, возрастное ограничение, кабинет |
| Кабинет | номер, этаж, количество мест |

Атрибут должен быть **атомарным**: не одно поле «ФИО», а отдельно `last_name`, `first_name` — тогда легко сортировать по фамилии.

## 3. Виды связей

Глаголы показывают связь: руководитель «ведёт» кружок, ученик «записывается» в кружок.

### Один-к-одному (1 : 1)

Одной записи во второй таблице соответствует **не более одной** записи.

Пример: ученик — ученический билет; государство — его столица; игрок — настройки его профиля.

Реализация: внешний ключ + `UNIQUE`. Чаще всего объединяются в одну таблицу; отдельная таблица создаётся для секретных или редко используемых данных.

```text
students (id PK, name)      student_cards (id PK, student_id FK UNIQUE, card_no, issued)
```

### Один-ко-многим (1 : N) — встречается чаще всего

Одной записи во второй таблице соответствует **много** записей, а наоборот — только одна.

Примеры: один руководитель — много кружков (у кружка — один руководитель); один класс — много учеников; одна область — много городов; один игрок — много результатов игр.

Реализация: внешний ключ добавляем **в таблицу на стороне «многих»**.

```text
teachers                      clubs
+----+------------------+     +----+---------------+------------+
| id | name             |     | id | title         | teacher_id |
+----+------------------+     +----+---------------+------------+
| 1  | Ермекова Г.С.    |<-+--| 1  | Python        |     1      |
| 2  | Жакыпов Т.Н.     |  +--| 2  | Веб-дизайн    |     1      |
+----+------------------+  +--| 3  | Робототехника |     2      |
       сторона «1»         |  +----+---------------+------------+
                           |          сторона «многих» → FK здесь
```

Почему FK на стороне «многих»? Если поставить `club_id` в таблицу `teachers`, несколько кружков одного руководителя не поместятся в одну ячейку.

### Многие-ко-многим (M : N)

Одной записи во второй таблице соответствует много записей, и **наоборот тоже** много.

Примеры: ученик — кружок (ученик в нескольких кружках, в кружке много учеников); ученик — предмет; актёр — фильм; товар — заказ.

В реляционной модели хранить связь M:N напрямую **невозможно**. Решение — **промежуточная (связующая) таблица**, которая разбивает M:N на две связи 1:N:

```text
students            enrollments (промежуточная таблица)          clubs
+----+---------+    +----+------------+---------+------------+   +----+---------------+
| id | name    |    | id | student_id | club_id | enrolled   |   | id | title         |
+----+---------+    +----+------------+---------+------------+   +----+---------------+
| 1  | Айгерим |<---| 1  |     1      |    1    | 2026-09-05 |-->| 1  | Python        |
| 2  | Даулет  |<-+-| 2  |     1      |    3    | 2026-09-12 |-->| 3  | Робототехника |
+----+---------+  +-| 3  |     2      |    1    | 2026-09-07 |   +----+---------------+
                    +----+------------+---------+------------+
```

Преимущество промежуточной таблицы — у **связи появляются свои атрибуты**: дата записи, статус оплаты, итоговая оценка.

Пара `(student_id, club_id)` не должна повторяться (один ученик не записывается в один кружок дважды) — ограничение `UNIQUE (student_id, club_id)`.

### Способ определения вида связи

Задаём два вопроса:
1. «Сколько **Б** соответствует одному **А**?» — один / много
2. «Сколько **А** соответствует одному **Б**?» — один / много

| Вопрос 1 | Вопрос 2 | Связь | Решение |
|---|---|---|---|
| один | один | 1 : 1 | FK + UNIQUE (или одна таблица) |
| много | один | 1 : N | FK на стороне «многих» |
| много | много | M : N | промежуточная таблица |

Пример: «Сколько кружков у одного руководителя?» — много. «Сколько руководителей у одного кружка?» — один. → **1 : N**, FK в таблице `clubs`.

## 4. ER-диаграмма

**ER-диаграмма (Entity–Relationship, «сущность–связь»)** — схема базы данных: прямоугольники — таблицы, линии — связи. На концах связей ставятся обозначения «1» и «N» (или «воронья лапка» — crow's foot).

```text
+-------------+        +-------------+        +--------------+        +-------------+
|  teachers   |        |    clubs    |        | enrollments  |        |  students   |
+-------------+        +-------------+        +--------------+        +-------------+
| PK id       |1      N| PK id       |1      N| PK id        |N      1| PK id       |
|    name     |--------|    title    |--------| FK club_id   |--------|    name     |
|    phone    |        | FK teacher_id|       | FK student_id|        |    birth    |
|    email    |        | FK room_id  |        |    enrolled  |        |    parent_ph|
+-------------+        +-------------+        +--------------+        +-------------+
                              |N
                              |1
                       +-------------+
                       |    rooms    |
                       +-------------+
                       | PK id       |
                       |    number   |
                       |    seats    |
                       +-------------+
```

Онлайн-инструменты (dbdiagram.io, drawdb.app) автоматически рисуют диаграмму по текстовому описанию.

## 5. Нормализация — устранение повторов

**Нормализация** — процесс разбиения таблиц на несколько, чтобы избавиться от повторов и аномалий. Для большинства прикладных баз данных достаточно первых трёх нормальных форм (НФ, NF).

Исходная «плохая» таблица:

| student | clubs | teacher | teacher_phone |
|---|---|---|---|
| Айгерим | Python, Робототехника | Ермекова, Жакыпов | 701..., 702... |
| Даулет | Python | Ермекова | 701... |

### Первая нормальная форма (1НФ): в каждой ячейке одно значение

Разбиваем списки на отдельные строки:

| student | club | teacher | teacher_phone |
|---|---|---|---|
| Айгерим | Python | Ермекова | 701... |
| Айгерим | Робототехника | Жакыпов | 702... |
| Даулет | Python | Ермекова | 701... |

### Вторая нормальная форма (2НФ): каждое поле зависит от всего ключа

Здесь ключ — (`student`, `club`). Но `teacher` зависит только от `club` (от части ключа). Поэтому выносим данные о кружке в отдельную таблицу: `clubs(id, title, teacher, teacher_phone)` и `enrollments(student_id, club_id)`.

### Третья нормальная форма (3НФ): неключевые поля не зависят друг от друга

В таблице `clubs` поле `teacher_phone` зависит не от кружка, а от **руководителя**. Выносим руководителя в отдельную таблицу: `teachers(id, name, phone)`, а в `clubs` — только `teacher_id`.

Итоговое правило (для лёгкого запоминания): **«Каждое поле должно зависеть от ключа, от всего ключа и ни от чего, кроме ключа».**

```text
Плохо (1 таблица)      →   Хорошо (4 таблицы)
student, clubs,             students(id, name)
teacher, teacher_phone      teachers(id, name, phone)
                            clubs(id, title, teacher_id → teachers)
                            enrollments(id, student_id → students, club_id → clubs, enrolled)
```

## 6. Преобразование в таблицы и правила именования

Распространённое соглашение об именах:
- имена таблиц — по-английски, строчными буквами, **во множественном числе**: `students`, `clubs`;
- поля — строчными буквами, слова через `_`: `first_name`, `birth_date`;
- первичный ключ — всегда `id`;
- внешний ключ — `<таблица_в_ед_числе>_id`: `teacher_id`, `club_id`;
- ключевые слова SQL — ЗАГЛАВНЫМИ БУКВАМИ: `CREATE TABLE`, `PRIMARY KEY`.

SQL-вид проекта (его можно выполнить в SQLite через модуль `sqlite3`):

```sql
CREATE TABLE teachers (
    id INTEGER PRIMARY KEY,
    last_name TEXT NOT NULL,
    first_name TEXT NOT NULL,
    phone TEXT UNIQUE
);

CREATE TABLE clubs (
    id INTEGER PRIMARY KEY,
    title TEXT NOT NULL UNIQUE,
    min_age INTEGER CHECK (min_age >= 6),
    teacher_id INTEGER REFERENCES teachers(id)
);

CREATE TABLE students (
    id INTEGER PRIMARY KEY,
    last_name TEXT NOT NULL,
    first_name TEXT NOT NULL,
    birth_date TEXT,
    parent_phone TEXT
);

CREATE TABLE enrollments (
    id INTEGER PRIMARY KEY,
    student_id INTEGER NOT NULL REFERENCES students(id),
    club_id INTEGER NOT NULL REFERENCES clubs(id),
    enrolled TEXT DEFAULT CURRENT_DATE,
    UNIQUE (student_id, club_id)
);
```

Порядок создания таблиц важен: сначала таблицы, **на которые ссылаются** (`teachers`), затем **ссылающиеся** таблицы (`clubs`), в конце — промежуточная таблица.

## 7. Описание и проверка проекта на Python

Схему можно записать в виде словаря и проверить её корректность программой — например, ссылается ли каждый FK на существующую таблицу:

```python
schema = {
    "teachers": {"pk": "id", "fields": ["id", "last_name", "first_name", "phone"], "fk": {}},
    "clubs": {"pk": "id", "fields": ["id", "title", "teacher_id"], "fk": {"teacher_id": "teachers"}},
    "students": {"pk": "id", "fields": ["id", "last_name", "first_name", "birth_date"], "fk": {}},
    "enrollments": {"pk": "id", "fields": ["id", "student_id", "club_id", "enrolled"],
                    "fk": {"student_id": "students", "club_id": "clubs"}},
}

for table, info in schema.items():
    for field, target in info["fk"].items():
        status = "OK" if target in schema and field in info["fields"] else "ОШИБКА"
        print(f"{table}.{field} → {target}.id : {status}")

# Определение вида связи: на сколько таблиц ссылается таблица через FK
junctions = [t for t, i in schema.items() if len(i["fk"]) >= 2]
print("Промежуточные таблицы (M:N):", junctions)
```

Результат:

```text
clubs.teacher_id → teachers.id : OK
enrollments.student_id → students.id : OK
enrollments.club_id → clubs.id : OK
Промежуточные таблицы (M:N): ['enrollments']
```

## Частые ошибки

**1. Внешний ключ на стороне «один».** Если поставить `club_id` в таблицу `teachers`, один руководитель сможет вести только один кружок. Правильно: FK — на стороне «многих» (`clubs.teacher_id`).

**2. Хранение связи M:N списком.** `students.clubs = "1,3,5"` — нарушается 1НФ, поиск и удаление затруднены. Правильно: промежуточная таблица `enrollments`.

**3. Повторы в промежуточной таблице.** Один ученик записывается в один кружок дважды. Правильно: `UNIQUE (student_id, club_id)`.

**4. Хранение одного значения в двух таблицах.** Телефон руководителя и в `teachers`, и в `clubs`. Правильно: только в `teachers`.

**5. Проект не проверен на соответствие требованиям.** Схема красивая, но не отвечает на вопрос «В какой день записался ученик?». Правильно: в конце проектирования для каждого вопроса заказчика проверить «из какой таблицы мы это возьмём?».

**6. Чрезмерное дробление.** Отдельная таблица для каждого поля (например, таблица `first_names`) — лишнее. Отдельная таблица нужна только если сущность — самостоятельный объект.

## Основные понятия

| Понятие | Объяснение |
|---|---|
| Предметная область | Часть реального мира, описываемая БД (школа, библиотека, магазин) |
| Сущность (entity) | Объект, данные о котором хранятся; превращается в таблицу |
| Атрибут | Характеристика сущности; превращается в поле |
| Связь 1:1 | Одной записи — одна запись |
| Связь 1:N | Одной записи — много записей; FK на стороне «многих» |
| Связь M:N | Многим записям — много записей; через промежуточную таблицу |
| Промежуточная таблица | Таблица, разбивающая связь M:N на две 1:N |
| ER-диаграмма | Схема таблиц и связей |
| Нормализация | Разбиение таблиц для устранения повторов и аномалий |
| Аномалия | Проблема добавления/изменения/удаления, вызванная плохой структурой |

## Примечание

- В SQLite связь «многие-ко-многим» часто задают составным первичным ключом вместо отдельного `id`: `PRIMARY KEY (student_id, club_id)` — он одновременно запрещает повторы.
- `REFERENCES` в SQLite проверяется только при включённом `PRAGMA foreign_keys = ON`; без него «битые» ссылки будут молча сохраняться.
- Для внешних ключей можно задать поведение при удалении родителя: `ON DELETE CASCADE` (удалить зависимые записи), `ON DELETE SET NULL` (обнулить ссылку) или `ON DELETE RESTRICT` (запретить удаление).
- Иногда сознательно допускают **денормализацию** (хранят вычисленный итог или копию значения) ради скорости чтения — но тогда за согласованностью данных следит программа.
- Схему, описанную словарём Python, удобно превращать в SQL генерацией строк, но имена таблиц и полей нельзя подставлять через параметры `?` — их проверяют по «белому списку» допустимых имён.
- Документация: https://www.sqlite.org/foreignkeys.html и https://www.sqlite.org/lang_createtable.html
