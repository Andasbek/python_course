## 1. Сортировка оставшейся работы: план на ограниченное время

Когда до срока осталось мало времени (например, 90 минут), сначала перечисляем **всё**, а потом выбираем **самое важное**:

1. Все открытые Issues + замечания code review + отзывы пользователей → один список.
2. Каждому пункту — уровень важности: **[К]** критично, **[В]** важно, **[П]** предложение, **[М]** мелочь.
3. Каждому пункту — оценка времени (в минутах), и **умножьте её на 1,5** (буфер на непредвиденное).
4. Выбирайте из списка в порядке [К] → [В] → [П] так, чтобы сумма времени не превышала ≈80% бюджета (здесь 70 минут). Оставшееся время — проверка, README, релиз.

Пример:
| № | Работа | Уровень | Оценка | ×1,5 | Выбрано |
|---|---|---|---|---|---|
| 1 | При пустой БД диаграмма выдаёт ошибку | [К] | 10 | 15 | да |
| 2 | В README неверная команда установки | [В] | 5 | 8 | да |
| 3 | Фильтр по месяцам (предложение рецензента) | [П] | 30 | 45 | да |
| 4 | Тёмная тема | [М] | 40 | 60 | — (позже) |
| | **Всего выбрано** | | | **68 мин** | |

Способ выбора можно превратить в программу (сортировка по составному ключу и жадный выбор):

```python
WORK = [
    ("При пустой БД диаграмма выдаёт ошибку", "К", 10),
    ("В README неверная команда установки", "В", 5),
    ("Фильтр по месяцам", "П", 30),
    ("Тёмная тема", "М", 40),
    ("Добавить граничные значения в тесты", "В", 15),
]
PRIORITY = {"К": 0, "В": 1, "П": 2, "М": 3}
BUDGET = 70          # минут
BUFFER = 1.5


def plan(work, budget=BUDGET):
    """Выбирает по важности, пока помещается в бюджет."""
    chosen, used, later = [], 0, []
    for title, level, minutes in sorted(work, key=lambda w: (PRIORITY[w[1]], w[2])):
        need = round(minutes * BUFFER)
        if used + need <= budget:
            chosen.append((title, need))
            used += need
        else:
            later.append(title)
    return chosen, used, later


chosen, used, later = plan(WORK)
for title, need in chosen:
    print(f"[ ] {title} — {need} мин")
print(f"Всего: {used} мин. Позже: {', '.join(later)}")
```

Результат:
```text
[ ] При пустой БД диаграмма выдаёт ошибку — 15 мин
[ ] В README неверная команда установки — 8 мин
[ ] Добавить граничные значения в тесты — 22 мин
Всего: 45 мин. Позже: Фильтр по месяцам, Тёмная тема
```

Обратите внимание: программа не выбрала «Фильтр по месяцам» (45 мин), потому что 45 + 45 = 90 > 70. В такой ситуации возможность можно **уменьшить**: «только текущий и прошлый месяц» — 15 минут.

Такой алгоритм называется **жадным**: на каждом шаге берётся лучший по приоритету вариант, который ещё помещается. Он не всегда даёт оптимум (это задача о рюкзаке), но прост и понятен.

## 2. Минимальные требования к стабильной версии

Если времени мало, возвращаемся к MVP и доводим до стабильности то, что есть:
- программа запускается по README в чистом окружении;
- Must-возможности из ТЗ работают;
- при неверном вводе программа не падает;
- данные сохраняются между запусками;
- в README: что, для кого, как запустить.

**Совет:** не добавляйте новых возможностей перед релизом. Проект «меньше, но работает» полезнее, чем «больше, но падает».

## 3. Исправление замечаний и патч-версия `v1.0.1`

1. На каждое замечание — Issue (с меткой `review`), при исправлении — `Closes #N`.
2. После каждого исправления: тесты (`python -m unittest discover -s tests`) + основные сценарии.
3. В CHANGELOG — раздел `[1.0.1]`: «Исправлено: ...».
4. Тег и релиз:
```bash
git tag -a v1.0.1 -m "Исправления по замечаниям"
git push origin main --tags
```

## 4. Описание проекта для заявки (конкурс, хакатон, портфолио)

Для конкурсов проектов, IT-соревнований и хакатонов обычно требуются:

| Документ | Содержание | Готовый материал из проекта |
|---|---|---|
| **Аннотация** (150–250 слов) | актуальность, цель, методы (технологии), результат, практическая значимость | разделы «Проблема и решение», «Возможности» в README |
| **Описание проекта** | введение, проектирование (ТЗ, архитектура, модель БД), реализация, тестирование, заключение | папка `docs/`: ТЗ, ER-диаграмма, тест-кейсы |
| **Презентация** | 7–10 слайдов | схема архитектуры, скриншоты |
| **Видео** (иногда) | демо на 2–3 минуты | запись экрана по сценарию демо |
| **Код** | ссылка на репозиторий | GitHub Release |

**Структура аннотации (образец):**
> **Актуальность.** Многие школьники не умеют планировать карманные деньги: в опросе 14 из 20 школьников не смогли объяснить, почему к концу месяца у них закончились деньги.
> **Цель:** создать приложение, которое помогает контролировать расходы и достигать цели накопления.
> **Методы:** Python, Tkinter (интерфейс), SQLite (база данных), Matplotlib (визуализация), открытый API валют; объектно-ориентированная архитектура, модульное тестирование (unittest, 24 теста).
> **Результат:** приложение с возможностями учёта операций, месячного отчёта, диаграммы по категориям, прогноза даты достижения цели; 5 пользователей тестировали его в течение 2 недель.
> **Практическая значимость:** приложение может использоваться на уроках финансовой грамотности.

Данные об истории проекта (сколько коммитов, сколько дней вы работали) полезны в заявке и на собеседовании. Их можно получить из Git:

```bash
git log --pretty=format:"%ad;%s" --date=short > docs/history.csv
```

```python
import csv
import io
from collections import Counter

# В настоящем проекте: open("docs/history.csv", encoding="utf-8")
HISTORY = """2027-04-20;Каркас проекта
2027-04-22;models.py: Category, Operation
2027-04-22;logic.py: баланс
2027-04-27;database.py: CRUD
2027-04-29;MVP: интерфейс объединён
2027-05-04;Тесты: 24 теста
2027-05-04;Исправление: пустая сумма (#12)
2027-05-11;Релиз 1.0
"""
rows = list(csv.reader(io.StringIO(HISTORY), delimiter=";"))
days = Counter(date for date, _ in rows)
print(f"Коммитов: {len(rows)}, рабочих дней: {len(days)}")
print(f"Период: {rows[0][0]} — {rows[-1][0]}")
print("Самый активный день:", days.most_common(1)[0])
```

Результат:
```text
Коммитов: 8, рабочих дней: 6
Период: 2027-04-20 — 2027-05-11
Самый активный день: ('2027-04-22', 2)
```

(`git log` выводит сначала новые коммиты; в примере данные даны от старых к новым.)

## 5. Дальнейшее развитие проекта

Проект не заканчивается релизом v1.0. Отложенные работы оставьте в Issues с меткой `enhancement` (или в milestone `v1.1`) и опишите в README в разделе «Планы на будущее». Естественное продолжение для оконного приложения — веб-версия на Flask: логика (`logic.py`) и слой данных (`database.py`) переиспользуются без изменений, меняется только интерфейс.

## Частые ошибки

**1. Начать без плана** — всё время уходит на одну мелочь (цвета), а критическая ошибка остаётся. Правильно: сначала несколько минут на планирование.

**2. Добавлять новую возможность перед релизом** — это нарушает стабильность.

**3. Не коммитить/не загружать исправления** — всё остаётся только на вашем компьютере. Каждые 30 минут — `commit` + `push`.

**4. Пытаться обновить тег** (переместить `v1.0` на новый коммит) — это запутывает историю. Правильно: новая версия — новый тег (`v1.0.1`).

**5. Перечислять в аннотации только технологии.** Читателю аннотации прежде всего важны **проблема** и **результат**; технологии — это инструмент.

## Основные понятия
| Понятие | Пояснение |
|---|---|
| Жадный алгоритм | на каждом шаге выбирает лучший доступный вариант, не пересматривая прошлые решения |
| Патч-версия | версия, содержащая только исправления ошибок (`1.0.1`) |
| Аннотация | краткое описание актуальности, цели, методов и результата проекта |
| Буфер | запас, добавляемый к оценённому времени (×1,5) |

## Примечание

- `sorted(..., key=lambda w: (PRIORITY[w[1]], w[2]))` сортирует по кортежу: сначала по первому элементу, при равенстве — по второму; так задаётся сортировка по нескольким признакам.
- `round()` в Python использует «банковское» округление: `round(2.5) == 2`, `round(3.5) == 4`; для оценки времени с запасом лучше `math.ceil()`.
- Тег нельзя «передвинуть» незаметно: после `git push` другие уже могли его скачать. Если тег ошибочен до публикации — `git tag -d v1.0.1` и создать заново.
- `git log --pretty=format:"..."` поддерживает поля `%h` (короткий хеш), `%an` (автор), `%ad` (дата), `%s` (сообщение); `--reverse` выводит коммиты от старых к новым.
- Документация: https://git-scm.com/docs/git-log и https://docs.python.org/3/howto/sorting.html
