## 1. Финальный чек-лист репозитория

Перед публикацией проверяем репозиторий «глазами незнакомого человека»:

| № | Проверка | Как |
|---|---|---|
| 1 | Нет секретных данных (ключей, паролей, личных данных) | `git log -p | findstr /i "key password"` (Windows) или `git log -p | grep -i -E "key|password"` |
| 2 | Нет лишних файлов: `venv/`, `__pycache__/`, `.db`, `.log`, `build/`, `dist/` | просмотреть страницу GitHub, `.gitignore` |
| 3 | `requirements.txt` полный | `pip install -r requirements.txt` в чистом окружении |
| 4 | Запускается по README | тест чистого окружения: `git clone` → новый `venv` → установка → запуск |
| 5 | Все тесты проходят | `python -m unittest discover -s tests` |
| 6 | Скриншоты видны, ссылки работают | открыть README на GitHub |
| 7 | Нет мёртвого кода, файлов вроде `test2.py` | просмотр дерева файлов, `git ls-files` |
| 8 | Репозиторий **открытый** (Public) | Settings → Danger Zone → Change visibility |
| 9 | Есть LICENSE, CHANGELOG | корень репозитория |

> Если секретные данные найдены в истории: удалить их из файла **недостаточно** — замените ключ на новый в самом сервисе (старый удалите): история Git хранит все прежние версии файлов.

## 2. Тег версии и GitHub Release

**Семантическое версионирование** (`MAJOR.MINOR.PATCH`): `1.0.0` — первая полная версия; `1.0.1` — исправление ошибки; `1.1.0` — новая возможность; `2.0.0` — большое изменение.

```bash
git status                       # всё закоммичено?
git tag -a v1.0 -m "Карманные деньги 1.0 — первая полная версия"
git push origin main --tags
```

**Release** — «страница» тега на GitHub: с описанием и файлами для скачивания.
1. В репозитории: **Releases → Draft a new release**.
2. **Choose a tag** → `v1.0`.
3. Название: `Карманные деньги 1.0`. Описание — раздел `1.0` из CHANGELOG.
4. По желанию прикрепите файл `.exe` (собранный PyInstaller).
5. **Publish release**.

Теперь любой может скачать именно эту стабильную версию, а разработка в `main` продолжается дальше.

## 3. Репозиторий — часть портфолио

Профиль GitHub с несколькими аккуратно оформленными проектами — это **портфолио** разработчика: его показывают на конкурсах проектов, при поступлении, на собеседовании.

| Что делаем | Где |
|---|---|
| Краткое описание (About) и ссылка на сайт/видео | страница репозитория → About (значок шестерёнки) |
| Темы (topics): `python`, `tkinter`, `sqlite`, `matplotlib` | About → Topics |
| Закрепление в профиле (Pin) — 4–6 лучших проектов | профиль → Customize your pins |
| README профиля (3–5 строк о себе) | специальный репозиторий с именем `<логин>/<логин>` |

Образец README профиля:
~~~markdown
# Привет, я — Алихан
Начинающий Python-разработчик из Алматы.

**Мои проекты:** Карманные деньги (Tkinter + SQLite + API), игра «Степной забег» (Pygame),
анализ качества воздуха в Алматы (Pandas + Matplotlib).

**Интересы:** анализ данных, разработка игр. Следующая цель — веб-разработка (Flask).
~~~

## 4. Структура технической презентации проекта

| № | Раздел | Содержание |
|---|---|---|
| 1 | Представление | название проекта, одно предложение о нём |
| 2 | **Проблема** | чья и какая проблема? Данные/пример |
| 3 | **Решение** | как проект решает проблему, чем отличается от аналогов |
| 4 | **Демо** | живая демонстрация 2–3 основных сценариев |
| 5 | **Техника** | архитектура (слои), технологии, модель БД, один интересный фрагмент кода |
| 6 | **Качество** | число тестов, найденные и исправленные ошибки, code review |
| 7 | **Будущее** | ограничения текущей версии, планы следующей |

**Расскажите историю:** «Каждый месяц я не знал, куда уходят мои деньги...» — запоминается гораздо лучше, чем список фактов.

## 5. Правила слайдов

| Правило | Пояснение |
|---|---|
| 7–10 слайдов | на каждый раздел 1–2 слайда |
| Один слайд — одна мысль | заголовок слайда — сама эта мысль: «Тесты: 24/24 пройдены» |
| Мало текста | не более 3–4 строк, в каждой 6–8 слов; полные предложения вы **говорите**, а не пишете |
| Крупный шрифт | не менее 24 pt (для кода 18 pt), должно читаться с последнего ряда |
| Картинка > текст | скриншот, схема архитектуры, ER-диаграмма, диаграмма |
| Код — только фрагмент | 8–12 строк, самое интересное место, с подсветкой |
| Единый стиль | 2–3 цвета, один шрифт; отлично, если совпадают с цветами проекта |
| Последний слайд | «Спасибо!» + ссылка/QR-код репозитория |

Плохой слайд: «Моя программа написана на языке Python и использует библиотеку Tkinter, а также базу данных SQLite...» (6 строк текста).
Хороший слайд: значки трёх технологий + схема архитектуры + одна строка: «Три слоя: интерфейс → логика → данные».

## 6. Демо: самая рискованная часть

Живая демонстрация — самая впечатляющая, но и самая опасная часть доклада. Есть выражение «эффект демо»: программа, безупречно работавшая у разработчика, падает перед аудиторией. Поэтому:

**Сценарий демо** — заранее записанные шаги (что нажимаю, что говорю):
```text
1. Программа открыта, в БД готовые данные за 2 недели.       "Это главное окно..."
2. Добавить расход: 800, Еда, "Обед" -> Сохранить.           "Ввод занимает 5 секунд..."
3. Диаграмма обновилась -> обратить внимание.                "Еда — 45% расходов..."
4. Неверный ввод: "абв" -> сообщение.                        "Программа устойчива к ошибкам..."
5. Прогноз цели: велосипед 60 000 тг -> дата.                "Моя любимая возможность..."
```

**Демо-данные:** демо с пустой БД — невпечатляющее. Заранее подготовьте реалистичные данные (отдельный файл `demo.db` или скрипт заполнения):

```python
"""tools/make_demo_db.py — создаёт реалистичные данные для демо."""
import datetime
import random
import sqlite3

rnd = random.Random(2027)            # каждый раз одинаковые данные
conn = sqlite3.connect(":memory:")   # в настоящем проекте: "demo.db"
conn.executescript("""
CREATE TABLE operation (id INTEGER PRIMARY KEY, category TEXT,
                        amount INTEGER, op_date TEXT);
""")
start = datetime.date(2027, 4, 1)
categories = {"Еда": (300, 1200), "Транспорт": (100, 200), "Развлечения": (500, 2500)}
rows = []
for day in range(40):
    d = (start + datetime.timedelta(days=day)).isoformat()
    for cat, (low, high) in categories.items():
        if rnd.random() < 0.6:
            rows.append((cat, rnd.randrange(low, high, 50), d))
with conn:
    conn.executemany("INSERT INTO operation (category, amount, op_date) VALUES (?, ?, ?)", rows)
total = conn.execute("SELECT COUNT(*), SUM(amount) FROM operation").fetchone()
print(f"Демо-данные: операций — {total[0]}, всего {total[1]} тг")
```

Результат (числа благодаря `seed` всегда одинаковые):
```text
Демо-данные: операций — 78, всего 54950 тг
```

**Запасной план (Plan B):**
| Что может случиться | Заранее подготовить |
|---|---|
| Программа упала | видео демо (1–2 мин) или скриншоты на слайдах |
| Нет интернета (API) | проверить, что кэш работает; показать это как «офлайн-режим» |
| На чужом компьютере нет Python/библиотек | свой ноутбук или `.exe`; заранее проверить на том компьютере, где будет показ |
| Экран маленький, другое разрешение проектора | увеличить размер окна, шрифт |
| Сломались демо-данные | скрипт `make_demo_db.py` пересоздаёт их за секунду |

## Частые ошибки

**1. Поставить тег при незакоммиченных изменениях.** `v1.0` указывает на старую версию. Правильно: сначала `git status` — «nothing to commit».

**2. Репозиторий остался закрытым (Private)** — по ссылке никто, кроме вас, его не откроет. Проверьте ссылку с другого аккаунта или в окне инкогнито.

**3. Читать текст со слайда.** Аудитория прочитает быстрее вас и перестанет слушать. Слайд — картинки и ключевые слова, текст — у вас в речи.

**4. Показывать демо на пустых данных** или тратить время демо на «сейчас заполню данные».

**5. Показывать весь код в технической части.** 200 строк кода на проекторе никто читать не будет. Один интересный фрагмент на 10 строк + схема архитектуры.

**6. Тег не отправлен на GitHub.** `git push` не отправляет теги по умолчанию. Правильно: `git push origin v1.0` или `git push --tags`.

## Основные понятия
| Понятие | Объяснение |
|---|---|
| Тег (tag) | постоянное имя, присвоенное коммиту (`v1.0`) |
| Release | публикация на GitHub на основе тега, с описанием и файлами |
| Семантическое версионирование | система нумерации версий `MAJOR.MINOR.PATCH` |
| Портфолио | собрание лучших работ (профиль GitHub) |
| Сценарий демо | заранее записанные шаги демонстрации |
| Запасной план (Plan B) | что делать, если что-то сломалось |

## Примечание

- Аннотированный тег (`git tag -a`) хранит автора, дату и сообщение, а лёгкий тег (`git tag v1.0`) — только указатель на коммит; для релизов используйте аннотированные.
- `random.Random(seed)` создаёт отдельный генератор: одинаковое зерно даёт одинаковую последовательность, при этом глобальный `random` в остальной программе не затрагивается.
- Номер версии удобно хранить в одном месте кода (`__version__ = "1.0.0"` в `qalta/__init__.py`) и показывать его в окне «О программе» и в заголовке.
- Для поиска секретов во всей истории существуют специальные инструменты (например, `git log -S "ключ"` ищет коммиты, где строка появилась или исчезла).
- Если в истории оказались секреты, их можно вычистить инструментом `git filter-repo`, но ключ всё равно нужно сменить — копии репозитория могли уже разойтись.
- Документация: https://docs.github.com/ru/repositories/releasing-projects-on-github и https://git-scm.com/book/ru/v2/Основы-Git-Работа-с-метками
