## 1. Аралық қарау деген не және не үшін?

**Code review (кодты рецензиялау)** — өзгерістер негізгі тармаққа немесе релизге түспес бұрын кодты басқа әзірлеушінің тексеруі. **Аралық қарау** — дәл осындай тексеру, бірақ бүкіл жобаға (MVP) және ол аяқталмай тұрып, түзетуге әлі уақыт барда жүргізіледі.

| | Код үзіндісін қарау | Жобаны аралық қарау |
|---|---|---|
| Не тексеріледі | бір өзгеріс (коммит, Pull Request) | бүкіл жоба (MVP) |
| Нәтиже | нақты жолдарға ескертулер | жақсарту жоспары (Issues) |
| Қарау бағыты | тек код | функционал, ыңғайлылық, код, құжат, ТТ-ға сәйкестік |

Code review пайдасы:
- **Қателерді ерте табу** — қатені релизге дейін түзету кейін түзеткеннен әлдеқайда арзан.
- **Сырттан көзқарас** — сізге түсінікті батырма басқаға түсініксіз болуы мүмкін.
- **Білім алмасу** — басқаның шешімінен жаңа тәсіл алуға болады, ал рецензент жобаның құрылымын біледі.
- **Бірыңғай стиль** — код біртіндеп ортақ ережелерге (PEP 8, команда келісімдері) келтіріледі.

## 2. Рецензия қалай өтеді: үш қадам

```text
1. Демонстрация (автор)              2. Тексеру (рецензент)               3. Пікір (рецензент)
   - идея және ТТ                       - бағдарламаны өзі іске қосады       - чек-парақ толтырады
   - негізгі сценарийлер                - «бұзып көреді»                     - 2–3 артықшылық
   - не дайын / не дайын емес           - кодты оқиды (3–4 файл)             - 3–5 ескерту + ұсыныс
```

**Автордың ережесі:** демонстрация кезінде ақталмаңыз, тек көрсетіңіз. Тексеру кезінде **үнсіз** отырыңыз — рецензент өзі адасып көрсін (прототиптің юзабилити-тестіндей).

**Рецензенттің ережесі:** сіз — бағалаушы емес, **көмекші**. Мақсат — жобаны жақсарту, автордың қатесін «ұстау» емес.

## 3. Аралық қараудың чек-парағы

**А. Функционал (бағдарлама іске қосылады және жұмыс істейді)**
- [ ] README бойынша іске қосылды (`pip install -r requirements.txt`, `python main.py`)
- [ ] ТТ-дағы Must-мүмкіндіктердің бәрі бар
- [ ] Қате енгізуде (бос, әріп, теріс сан, өте ұзын мәтін) құламайды
- [ ] Деректер бағдарламаны қайта ашқанда сақталған
- [ ] ТТ-да көрсетілген барлық технология (ДҚ, API, графика т.б.) шынымен қосылған және жұмыс істейді

**Ә. Ыңғайлылық**
- [ ] Не істеу керегі түсіндірмесіз түсінікті
- [ ] Хабарламалар қазақ тілінде, түсінікті
- [ ] Әрекеттің нәтижесі көрінеді («Сақталды», экран жаңарады)

**Б. Код сапасы**
- [ ] Қабаттар бөлек (интерфейс / логика / деректер)
- [ ] Атаулар мағыналы, PEP 8 сақталған
- [ ] Функциялар қысқа (≈30 жолдан аспайды), қайталанатын код жоқ
- [ ] Docstring және қажетті жерде түсініктеме бар
- [ ] SQL параметрлері `?` арқылы; құпия деректер кодта жоқ

**В. Репозиторий**
- [ ] Құрылым түсінікті, `.gitignore` бар, артық файлдар (`venv`, `.db`, `__pycache__`) жоқ
- [ ] Коммиттер жүйелі, хабарламалары мағыналы

## 4. Пікірді қалай жазамыз?

### Жақсы пікірдің формуласы
> **Не көрдім** (нақты орын) + **неге маңызды** (салдары) + **не ұсынамын** (жол)

| Жаман пікір | Неге жаман | Жақсы пікір |
|---|---|---|
| «Код нашар» | нақты емес, ренжітеді | «`gui.py`, 120–180 жолдар: `on_save` 60 жол — оқу қиын. Тексеруді `_validate()` әдісіне бөлуді ұсынамын.» |
| «Батырма дұрыс емес» | қай батырма? неге? | «“Del” батырмасы растаусыз бәрін өшіреді — кездейсоқ басып қалуға болады. `askyesno` қосуды ұсынамын.» |
| «Бәрі керемет!» | пайдасы жоқ | «Санатты Combobox-пен таңдау өте ыңғайлы — қате енгізу мүмкін емес. Осы тәсілді күнге де қолдануға болады.» |
| «Мен болсам бәрін қайта жазар едім» | орындалмайтын кеңес | «Деректер қорымен жұмыс `main.py`-де; оны жеке `database.py`-ге шығару 30 минут алады, бірақ тестілеуді жеңілдетеді.» |

**Ережелер:**
1. Адамды емес, **кодты** талқылаңыз: «сен қате жаздың» емес, «бұл функцияда қате бар».
2. **Сұрақ түрінде** жазуға болады: «Мұнда `None` келсе не болады?»
3. Кемінде **екі артықшылық** жазыңыз — автор нені сақтап қалу керегін білсін.
4. Әр ескертуге **маңыздылық деңгейін** қойыңыз.

### Ескертулердің маңыздылық деңгейлері
| Деңгей | Мағынасы | Мысал |
|---|---|---|
| **[С] Сыни** | бағдарлама құлайды, деректер жоғалады, қауіпсіздік | бос өрісте `ValueError`, API кілті кодта |
| **[М] Маңызды** | талап орындалмайды, пайдаланушы адасады | Must-мүмкіндік жоқ, нәтиже көрінбейді |
| **[Ұ] Ұсыныс** | код сапасы, ыңғайлылық | ұзын функция, түсініксіз атау |
| **[Т] Ұсақ-түйек** | дәм, стиль | бос орындар, батырманың түсі |

## 5. Пікірді қабылдау және өңдеу

Пікір алу — ыңғайсыз сезім болуы мүмкін. Бұл қалыпты. Есте сақтаңыз: **пікір — сіз туралы емес, жоба туралы** және ол жобаны жақсартуға берілген тегін көмек.

**Автордың әрекеттері:**
1. Тыңдаңыз, **дауласпаңыз**; түсініксіз болса, нақтылаңыз: «Қай жерде адастың? Көрсетіп жібересің бе?»
2. «Рахмет» деңіз — тіпті келіспесеңіз де.
3. Барлық пікірді жазып алыңыз.
4. Әр пікір бойынша шешім қабылдаңыз: **қабылдаймын / кейін / қабылдамаймын (себебімен)**.

### «Әсер — күш» матрицасы
Барлық ескертуді түзетуге уақыт жетпейді. Басымдықты анықтаймыз:

```text
                 Аз күш                    Көп күш
            ┌────────────────────────┬────────────────────────┐
 Үлкен әсер │ 1. ҚАЗІР жасау          │ 2. ЖОСПАРЛАУ           │
            │ (растау қосу, хабарлама)│ (модульге бөлу, тест)  │
            ├────────────────────────┼────────────────────────┤
 Аз әсер    │ 3. Уақыт болса          │ 4. ЖАСАМАУ             │
            │ (атауды түзету, түс)    │ (бәрін қайта жазу)     │
            └────────────────────────┴────────────────────────┘
```

Сыни [С] ескертулер әрқашан 1-ші немесе 2-ші шаршыда.

### Пікірлерді GitHub Issues-ке тіркеу
Әр қабылданған ескерту — жеке issue, белгісімен (`bug`, `review`, `ux`) және milestone-мен (`v1.0`). Түзетілгенде коммитте `Closes #12` деп жазамыз.

### Пікірлерге жауап журналы (`docs/review.md`)
| № | Пікір (кімнен) | Деңгей | Шешім | Issue / коммит |
|---|---|---|---|---|
| 1 | Бос сомада бағдарлама құлайды (Айдана) | [С] | Қабылданды, түзетілді | #12, `a1b2c3d` |
| 2 | Диаграмма түстері ұқсас (Ерлан) | [Т] | Кейін (v1.1) | #13 |
| 3 | SQLite-ты JSON-ға ауыстыру (Ерлан) | [Ұ] | Қабылданбады: ТТ бойынша JOIN-ды сұраныстар керек | — |

Мұндай журнал сыртқы пікір бойынша қандай шешімдер қабылданғанын және неліктен екенін көрсетеді.

## 6. GitHub-тағы code review: Pull Request

Командалық әзірлеуде код **Pull Request (PR)** арқылы тексеріледі — бұл өзгерістері бар тармақты `main`-ге біріктіру сұранысы:

```bash
git switch -c fix/empty-amount          # түзетуге арналған жаңа тармақ
# ... кодты түзетеміз ...
git add qalta/gui.py
git commit -m "Сақтау алдында бос соманы тексеру (#12)"
git push -u origin fix/empty-amount     # тармақты GitHub-қа жібереміз
```

Әрі қарай GitHub-та: **Compare & pull request** → сипаттама (не және неге өзгерді) → **Create pull request**. Рецензент **Files changed** қойындысында:
- нақты жолға түсініктеме қалдырады (жолдың сол жағындағы «+» белгісі);
- ```` ```suggestion ```` блогымен дайын түзету ұсына алады;
- қарауды үш нұсқаның бірімен аяқтайды: **Comment** (жай түсініктеме), **Approve** (мақұлдау), **Request changes** (түзету керек).

Мақұлданғаннан кейін PR біріктіріледі (**Merge**), тармақ өшіріледі. PR сипаттамасында `Closes #12` деп жазылса, issue автоматты түрде жабылады.

> **Кеңес:** шағын PR-ды (200–300 жолға дейін) үлкенінен жылдамырақ әрі мұқиятырақ тексереді.

## 7. Мысал: пікірге дейін және кейін

Рецензент пікірлері:
```python
def f(d):                          # [Ұ] атаулар түсініксіз: f, d
    s = 0
    for i in range(len(d)):        # [Ұ] range(len(...)) — тікелей итерация жеңілірек
        if d[i][2] == "шығыс":     # [Ұ] [2] — сиқырлы индекс
            s = s + d[i][1]
    return s / len(d)              # [С] бос тізімде ZeroDivisionError
```

Түзетілген нұсқа:
```python
def average_expense(operations):
    """Шығыс операцияларының орташа сомасы; шығыс жоқ болса 0."""
    expenses = [op["amount"] for op in operations if op["kind"] == "шығыс"]
    if not expenses:
        return 0
    return sum(expenses) / len(expenses)


ops = [{"amount": 3000, "kind": "кіріс"}, {"amount": 800, "kind": "шығыс"},
       {"amount": 400, "kind": "шығыс"}]
print(average_expense(ops))
print(average_expense([]))
```

Нәтижесі:
```text
600.0
0
```

Назар аударыңыз: түпнұсқа функция бұрыс та есептеген — шығыстар қосындысын **барлық** операциялар санына бөлген. Рецензенттің «атаулар түсініксіз» деген қарапайым ескертуі логикалық қатені табуға көмектесті.

## Жиі кездесетін қателер

**1. Тек «бәрі жақсы» деп жазу.** Пайдасыз пікір. Чек-парақтың әр бөлімінен кемінде бір нақты бақылау жазыңыз.

**2. Тек кемшіліктерді жазу.** Автор нені сақтау керегін білмейді және көңілі түседі. Кемінде 2 артықшылық.

**3. Әр пікірге дауласу.** «Ол сенде дұрыс жұмыс істемеді, менде жұмыс істейді» — бұл да маңызды ақпарат: басқа компьютерде іске қосылмау — нақты қате (мысалы, абсолют жол, `requirements.txt` толық емес).

**4. Барлық пікірді бірден түзетуге тырысу** — нәтижесінде бәрі жарты-жартылай қалады. «Әсер–күш» матрицасын қолданыңыз.

**5. Пікірді жазып алмау.** Бір аптадан кейін ұмытылады. Бірден Issues-ке.

**6. Түзетуді тексермеу.** Бір қатені түзетіп, басқасын бұзу жиі болады. Әр түзетуден кейін негізгі (MVP) сценарийлерді қайта өтіп, тесттерді іске қосыңыз.

## Негізгі ұғымдар
| Ұғым | Түсіндірме |
|---|---|
| Аралық қарау | аяқталмаған жобаны сырттан бағалау |
| Рецензент | кодты/жобаны тексеретін адам |
| Чек-парақ | тексерілетін пункттердің тізімі |
| Маңыздылық деңгейі | ескертудің салдарына қарай басымдығы (сыни, маңызды, ұсыныс, ұсақ-түйек) |
| «Әсер–күш» матрицасы | түзетулерді пайдасы мен қажетті уақыты бойынша сұрыптау |
| Пікірлерге жауап журналы | әр ескерту бойынша қабылданған шешімдердің тізімі |
| Pull Request | GitHub-та өзгерістерді тексеріп, біріктіруге сұраныс |

## Ескерту

- Стиль туралы көп ескертуді автоматтандыруға болады: `flake8` немесе `ruff` PEP 8-ге сәйкестікті тексереді, `black` немесе `ruff format` кодты пішімдейді — сонда review-де бос орындар емес, логика талқыланады.
- `python -m pyflakes файл.py` (немесе `ruff check`) пайдаланылмаған импорттар мен айнымалыларды табады — жетілдіруден кейінгі жиі «қоқыс».
- Review-ге жібермес бұрын өз өзгерістеріңізді қараңыз: `git diff` (индекске қосылмағандар) және `git diff --staged` (`git add` арқылы қосылғандар).
- PEP 8 тікелей айтады: бір жоба ішіндегі бірізділік нұсқаулықты сөзбе-сөз орындаудан маңыздырақ — «біздің жобада бұлай жазылмайды» деген ескерту де салмақты.
- Нұсқаулықтар: PEP 8 — https://peps.python.org/pep-0008/, Pull Request туралы — https://docs.github.com/ru/pull-requests
