## 1. Что такое промежуточный просмотр и зачем он нужен?

**Code review (рецензирование кода)** — проверка кода другим разработчиком до того, как изменения попадут в основную ветку или в релиз. **Промежуточный просмотр** — то же самое для всего проекта (MVP) до его завершения, пока на исправления ещё есть время.

| | Обзор фрагмента кода | Промежуточный просмотр проекта |
|---|---|---|
| Что проверяется | одно изменение (коммит, Pull Request) | весь проект (MVP) |
| Результат | замечания к конкретным строкам | план улучшений (Issues) |
| Направление просмотра | только код | функционал, удобство, код, документация, соответствие ТЗ |

Польза code review:
- **Раннее обнаружение ошибок** — исправить ошибку до релиза намного дешевле, чем после.
- **Взгляд со стороны** — понятная вам кнопка может быть непонятна другому.
- **Обмен знаниями** — из чужого решения можно взять новый приём, а рецензент узнаёт устройство проекта.
- **Единый стиль** — код постепенно приводится к общим правилам (PEP 8, договорённости команды).

## 2. Как проходит рецензия: три шага

```text
1. Демонстрация (автор)              2. Проверка (рецензент)                3. Отзыв (рецензент)
   - идея и ТЗ                          - сам запускает программу             - заполняет чек-лист
   - основные сценарии                  - «пробует сломать»                   - 2–3 достоинства
   - что готово / что не готово         - читает код (3–4 файла)              - 3–5 замечаний + предложения
```

**Правило автора:** во время демонстрации не оправдывайтесь, а просто показывайте. Во время проверки сидите **молча** — пусть рецензент сам попробует запутаться (как при юзабилити-тесте прототипа).

**Правило рецензента:** вы не оценщик, а **помощник**. Цель — улучшить проект, а не «поймать» автора на ошибке.

## 3. Чек-лист промежуточного просмотра

**А. Функционал (программа запускается и работает)**
- [ ] Запустилась по README (`pip install -r requirements.txt`, `python main.py`)
- [ ] Есть все Must-возможности из ТЗ
- [ ] Не падает при неверном вводе (пусто, буквы, отрицательное число, очень длинный текст)
- [ ] Данные сохраняются при повторном открытии программы
- [ ] Все заявленные в ТЗ технологии (БД, API, графика и т.п.) реально подключены и работают

**Б. Удобство**
- [ ] Понятно без объяснений, что делать
- [ ] Сообщения на понятном языке
- [ ] Результат действия виден («Сохранено», экран обновляется)

**В. Качество кода**
- [ ] Слои разделены (интерфейс / логика / данные)
- [ ] Имена осмысленные, соблюдается PEP 8
- [ ] Функции короткие (не длиннее ≈30 строк), нет повторяющегося кода
- [ ] Есть docstring и, где нужно, комментарии
- [ ] Параметры SQL через `?`; секретных данных в коде нет

**Г. Репозиторий**
- [ ] Структура понятная, есть `.gitignore`, нет лишних файлов (`venv`, `.db`, `__pycache__`)
- [ ] Коммиты регулярные, сообщения осмысленные

## 4. Как писать отзыв?

### Формула хорошего отзыва
> **Что увидел** (конкретное место) + **почему это важно** (последствия) + **что предлагаю** (путь)

| Плохой отзыв | Почему плохо | Хороший отзыв |
|---|---|---|
| «Код плохой» | неконкретно, обидно | «`gui.py`, строки 120–180: `on_save` — 60 строк, трудно читать. Предлагаю вынести проверку в метод `_validate()`.» |
| «Кнопка неправильная» | какая кнопка? почему? | «Кнопка “Del” удаляет всё без подтверждения — можно нажать случайно. Предлагаю добавить `askyesno`.» |
| «Всё отлично!» | бесполезно | «Выбор категории через Combobox очень удобен — ошибочный ввод невозможен. Этот же приём можно применить и для даты.» |
| «Я бы всё переписал» | невыполнимый совет | «Работа с базой данных находится в `main.py`; вынос её в отдельный `database.py` займёт 30 минут, но упростит тестирование.» |

**Правила:**
1. Обсуждайте **код**, а не человека: не «ты написал неправильно», а «в этой функции ошибка».
2. Можно писать **в форме вопроса**: «Что будет, если сюда придёт `None`?»
3. Напишите не менее **двух достоинств** — чтобы автор знал, что нужно сохранить.
4. Для каждого замечания укажите **уровень важности**.

### Уровни важности замечаний
| Уровень | Значение | Пример |
|---|---|---|
| **[К] Критично** | программа падает, данные теряются, безопасность | `ValueError` при пустом поле, API-ключ в коде |
| **[В] Важно** | требование не выполнено, пользователь путается | нет Must-возможности, результат не виден |
| **[П] Предложение** | качество кода, удобство | длинная функция, непонятное имя |
| **[М] Мелочь** | вкус, стиль | пробелы, цвет кнопки |

## 5. Принятие и обработка отзывов

Получать отзыв может быть неприятно. Это нормально. Помните: **отзыв — не о вас, а о проекте**, и это бесплатная помощь в его улучшении.

**Действия автора:**
1. Слушайте, **не спорьте**; если непонятно — уточните: «Где ты запутался? Покажешь?»
2. Скажите «спасибо» — даже если не согласны.
3. Запишите все отзывы.
4. По каждому отзыву примите решение: **принимаю / позже / не принимаю (с причиной)**.

### Матрица «эффект — усилия»
На исправление всех замечаний времени не хватит. Определяем приоритеты:

```text
                   Мало усилий               Много усилий
            ┌────────────────────────────┬────────────────────────┐
 Большой    │ 1. СДЕЛАТЬ СЕЙЧАС          │ 2. ЗАПЛАНИРОВАТЬ       │
 эффект     │ (подтверждение, сообщение) │ (разбить на модули,    │
            │                            │  тесты)                │
            ├────────────────────────────┼────────────────────────┤
 Малый      │ 3. Если будет время        │ 4. НЕ ДЕЛАТЬ           │
 эффект     │ (исправить имя, цвет)      │ (переписать всё)       │
            └────────────────────────────┴────────────────────────┘
```

Критичные замечания [К] всегда попадают в 1-й или 2-й квадрат.

### Регистрация отзывов в GitHub Issues
Каждое принятое замечание — отдельный issue с меткой (`bug`, `review`, `ux`) и milestone (`v1.0`). При исправлении пишем в коммите `Closes #12`.

### Журнал ответов на отзывы (`docs/review.md`)
| № | Отзыв (от кого) | Уровень | Решение | Issue / коммит |
|---|---|---|---|---|
| 1 | Программа падает при пустой сумме (Айдана) | [К] | Принято, исправлено | #12, `a1b2c3d` |
| 2 | Цвета диаграммы похожи (Ерлан) | [М] | Позже (v1.1) | #13 |
| 3 | Заменить SQLite на JSON (Ерлан) | [П] | Не принято: по ТЗ нужны запросы с JOIN | — |

Такой журнал показывает, какие решения приняты по внешней обратной связи и почему.

## 6. Code review на GitHub: Pull Request

В командной разработке код проверяют через **Pull Request (PR)** — запрос на слияние ветки с изменениями в `main`:

```bash
git switch -c fix/empty-amount          # новая ветка для исправления
# ... правим код ...
git add qalta/gui.py
git commit -m "Проверка пустой суммы перед сохранением (#12)"
git push -u origin fix/empty-amount     # отправляем ветку на GitHub
```

Далее на GitHub: **Compare & pull request** → описание (что и зачем изменено) → **Create pull request**. Рецензент на вкладке **Files changed**:
- оставляет комментарий к конкретной строке (значок «+» слева от строки);
- может предложить готовую правку блоком ```` ```suggestion ````;
- завершает просмотр одним из вариантов: **Comment** (просто комментарий), **Approve** (одобрить), **Request changes** (нужны исправления).

После одобрения PR сливают (**Merge**), ветку удаляют. Если в описании PR написано `Closes #12`, issue закроется автоматически.

> **Совет:** небольшой PR (до 200–300 строк) проверяют быстрее и внимательнее, чем огромный.

## 7. Пример: до и после отзыва

Замечания рецензента:
```python
def f(d):                          # [П] непонятные имена: f, d
    s = 0
    for i in range(len(d)):        # [П] range(len(...)) — прямая итерация проще
        if d[i][2] == "расход":    # [П] [2] — магический индекс
            s = s + d[i][1]
    return s / len(d)              # [К] ZeroDivisionError на пустом списке
```

Исправленная версия:
```python
def average_expense(operations):
    """Средняя сумма расходных операций; если расходов нет — 0."""
    expenses = [op["amount"] for op in operations if op["kind"] == "расход"]
    if not expenses:
        return 0
    return sum(expenses) / len(expenses)


ops = [{"amount": 3000, "kind": "доход"}, {"amount": 800, "kind": "расход"},
       {"amount": 400, "kind": "расход"}]
print(average_expense(ops))
print(average_expense([]))
```

Результат:
```text
600.0
0
```

Обратите внимание: исходная функция ещё и считала неправильно — делила сумму расходов на число **всех** операций. Простое замечание рецензента «непонятные имена» помогло найти логическую ошибку.

## Частые ошибки

**1. Писать только «всё хорошо».** Бесполезный отзыв. Запишите хотя бы одно конкретное наблюдение по каждому разделу чек-листа.

**2. Писать только недостатки.** Автор не знает, что сохранить, и расстраивается. Не менее 2 достоинств.

**3. Спорить с каждым отзывом.** «У тебя не сработало, а у меня работает» — это тоже важная информация: незапуск на другом компьютере — реальная ошибка (например, абсолютный путь, неполный `requirements.txt`).

**4. Пытаться исправить все отзывы сразу** — в итоге всё остаётся наполовину. Используйте матрицу «эффект–усилия».

**5. Не записать отзыв.** Через неделю он забудется. Сразу в Issues.

**6. Не проверить исправление.** Часто, исправив одну ошибку, ломают другое. После каждого исправления заново пройдите основные (MVP) сценарии и запустите тесты.

## Основные понятия
| Понятие | Объяснение |
|---|---|
| Промежуточный просмотр | внешняя оценка незавершённого проекта |
| Рецензент | человек, проверяющий код/проект |
| Чек-лист | список проверяемых пунктов |
| Уровень важности | приоритет замечания в зависимости от последствий (критично, важно, предложение, мелочь) |
| Матрица «эффект–усилия» | сортировка исправлений по пользе и необходимому времени |
| Журнал ответов на отзывы | список решений, принятых по каждому замечанию |
| Pull Request | запрос на GitHub на проверку и слияние изменений |

## Примечание

- Многие замечания о стиле можно автоматизировать: `flake8` или `ruff` проверяют соответствие PEP 8, `black` или `ruff format` форматируют код — тогда на review обсуждают логику, а не пробелы.
- `python -m pyflakes файл.py` (или `ruff check`) находит неиспользуемые импорты и переменные — частый «мусор» после доработок.
- Перед отправкой на review посмотрите свои изменения сами: `git diff` (несохранённые в индексе) и `git diff --staged` (уже добавленные через `git add`).
- PEP 8 прямо говорит: согласованность внутри одного проекта важнее, чем буквальное следование руководству — замечание «так не принято у нас в проекте» тоже весомое.
- Руководства: PEP 8 — https://peps.python.org/pep-0008/, о Pull Request — https://docs.github.com/ru/pull-requests
