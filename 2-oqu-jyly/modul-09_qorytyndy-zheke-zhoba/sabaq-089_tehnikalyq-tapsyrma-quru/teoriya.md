## 1. Техникалық тапсырма деген не

**Техникалық тапсырма (ТТ)** — жасалатын бағдарламаға қойылатын талаптарды, оның мүмкіндіктерін, шектеулерін және қабылдау шарттарын сипаттайтын құжат.

**Не үшін керек:**
- **Не жасаймыз** және, маңыздысы, **не жасамаймыз** — ауқымның шекарасы;
- жұмысты кезеңдерге бөлу және уақытты жоспарлау;
- архитектура мен деректер қорын жобалауға негіз;
- тестілеу үшін — «дұрыс жұмыс істейді» дегеннің нақты анықтамасы;
- жобаны тапсырғанда — «жоспарланғанның қаншасы орындалды» деген сұраққа жауап.

Нақты өндірісте ТТ ондаған бет болуы мүмкін (Қазақстанда да, ТМД-да да ГОСТ 34 стандарты бар). Шағын жобаға **3–5 беттік** жеңілдетілген нұсқа жеткілікті.

## 3. Функционалдық және функционалдық емес талаптар

| | Функционалдық | Функционалдық емес |
|---|---|---|
| Сұрақ | Бағдарлама **не істейді**? | Бағдарлама **қалай / қандай** жұмыс істейді? |
| Мысал | «Пайдаланушы тест тақырыбын таңдай алады» | «Нәтижелер графигі 2 секундтан аз уақытта ашылады» |
| Мысал | «Бағдарлама нәтижені деректер қорына сақтайды» | «Бағдарлама Windows 10/11 және Linux-та жұмыс істейді» |
| Мысал | «Нәтижелерді CSV-ге экспорттауға болады» | «Пароль хэш түрінде сақталады» |
| Мысал | | «Интерфейс қазақ тілінде, шрифт кемінде 12 pt» |

**Функционалдық емес талаптардың түрлері:** өнімділік (жылдамдық, көлем), сенімділік (қате енгізуде құламау, деректер жоғалмауы), ыңғайлылық (тіл, түсініктілік, қолжетімділік), қауіпсіздік (құпиялар, парольдер, енгізу), портативтілік (ОЖ, Python нұсқасы), қолдау (код сапасы, тесттер, құжаттама).

## 4. Жақсы талаптың белгілері

Талап **нақты**, **тексерілетін**, **бір мәнді** болуы керек.

| Нашар талап | Неге нашар | Жақсы талап |
|---|---|---|
| «Бағдарлама ыңғайлы болуы керек» | Тексеруге болмайды | «Кез келген негізгі әрекет басты терезеден 2 рет басудан аспайтын қашықтықта» |
| «Бағдарлама жылдам жұмыс істейді» | «Жылдам» — қаншалықты? | «1000 жазбаны іздеу 1 секундтан аз» |
| «Статистика көрсетіледі» | Қандай? Қалай? | «Пайдаланушы тақырыптар бойынша дұрыс жауап пайызының бағаналы диаграммасын көре алады» |
| «Деректер сақталады» | Қайда? Қашан? | «Әр тест аяқталғанда нәтиже (күні, тақырып, балл) SQLite базасына автоматты түрде сақталады» |
| «Қателер болмауы керек» | Мүмкін емес | «Сан күтілетін өріске мәтін енгізілсе, бағдарлама құламайды, ескерту терезесін шығарады» |

**«Қалай?» сынағы:** талапты оқып, «оны қалай тексеремін?» деп сұраңыз. Жауап таппасаңыз — талап бұлдыр.

## 5. Пайдаланушы тарихы (user story)

Талаптарды пайдаланушы көзқарасынан жазудың қалыптасқан түрі:

```text
Мен [РӨЛ] ретінде [ӘРЕКЕТ] жасағым келеді, себебі [МАҚСАТ / ПАЙДА].
```

Мысалдар («ҰБТ тренажері»):
- US-1. *Мен оқушы ретінде тақырыпты таңдап, 10 сұрақтан тұратын тест тапсырғым келеді, себебі сол тақырыпты тексергім келеді.*
- US-2. *Мен оқушы ретінде тест аяқталғанда дұрыс және қате жауаптарымды көргім келеді, себебі қатемнен үйренгім келеді.*
- US-3. *Мен оқушы ретінде тақырыптар бойынша нәтижелерімнің графигін көргім келеді, себебі әлсіз тақырыптарымды білгім келеді.*
- US-4. *Мен мұғалім ретінде сұрақтарды CSV файлдан жүктегім келеді, себебі сұрақтарды бір-бірлеп енгізу ұзақ.*

**Неге «себебі» маңызды?** Ол мүмкіндіктің **неге** керек екенін түсіндіреді және басқа, қарапайым шешім табуға көмектеседі.

### Қабылдау критерийлері

Әр user story-ге «дайын» деп есептеудің нақты шарттары жазылады. Ыңғайлы формат — **«Берілгені — Әрекет — Нәтиже»** (Given — When — Then):

```text
US-2. Тест нәтижесін көру
  Қабылдау критерийлері:
  1. Берілгені: оқушы 10 сұраққа жауап берді.
     Әрекет: «Аяқтау» батырмасын басады.
     Нәтиже: «Нәтиже: 7/10 (70%)» түріндегі жазу көрсетіледі.
  2. Нәтиже терезесінде әр қате жауап үшін сұрақ, оқушының жауабы және дұрыс жауап көрсетіледі.
  3. Нәтиже деректер қорына күні және тақырыбымен сақталады.
  4. Бірде-бір сұраққа жауап берілмесе, «Аяқтау» батырмасы «Кемінде бір сұраққа жауап беріңіз» ескертуін шығарады.
```

Қабылдау критерийлері кейін **тесттерге** оңай айналады (`unittest`):

```python
import unittest


def natije_matini(dures, barlygy):
    """Тест нәтижесін «7/10 (70%)» түрінде қайтарады."""
    if barlygy == 0:
        raise ValueError("Сұрақтар саны 0 болмауы керек")
    return f"{dures}/{barlygy} ({dures * 100 // barlygy}%)"


class TestUS2(unittest.TestCase):
    """US-2 қабылдау критерийлерінің 1-пункті."""

    def test_natije_matini(self):
        self.assertEqual(natije_matini(7, 10), "7/10 (70%)")

    def test_nol_suraq(self):
        with self.assertRaises(ValueError):
            natije_matini(0, 0)


if __name__ == "__main__":
    unittest.main()
```

## 6. Басымдық: MoSCoW әдісі

Барлық идеяны бірдей маңызды деп санасақ, ештеңе аяқталмайды. **MoSCoW** әдісі мүмкіндіктерді 4 топқа бөледі:

| Топ | Мағынасы | Үлесі (шамамен) | Мысал (ҰБТ тренажері) |
|---|---|---|---|
| **M**ust have — міндетті | Онсыз жоба мағынасыз; MVP | ≈ 60% уақыт | Тест тапсыру, нәтиже, сақтау, график |
| **S**hould have — маңызды | Өте пайдалы, бірақ онсыз да жұмыс істейді | ≈ 20% | CSV-ден импорт, қате жауаптарды қайталау |
| **C**ould have — болса жақсы | Уақыт қалса | ≈ 20% | Таймер, түнгі тақырып, дыбыс |
| **W**on't have (this time) — бұл жолы жоқ | Әдейі жоспардан шығарылды | 0% | Онлайн рейтинг, мобильді нұсқа |

«Won't have» тізімі — ауқымды қорғайтын маңызды бөлім: «Неге мобильді нұсқа жоқ?» деп сұраса, «Бұл ТТ-да әдейі шығарылған, келесі нұсқада» деп жауап бересіз.

## 8. ТТ-ның өзгеруі

ТТ — «тасқа қашалған» құжат емес. Әзірлеу барысында бірдеңе өзгерсе (мүмкіндік тым қиын болып шықты, жаңа идея келді), ТТ-ны **жаңартып**, нұсқасын көтереміз (1.0 → 1.1) және соңында «Өзгерістер тарихы» бөліміне жазамыз. Маңыздысы — өзгерісті **саналы** түрде жасау, «өздігінен» емес.

## Жиі кездесетін қателер

**1. ТТ-да «қалай» жазу, «не» емес.** «`Toplevel` терезесінде `Listbox` болады» — бұл іске асыру (архитектура, интерфейс). ТТ-да: «Пайдаланушы барлық тақырыптардың тізімін көріп, біреуін таңдай алады».

**2. Тек Must.** Бәрі «міндетті» болса — басымдық жоқ; уақыт жетпегенде нені алып тастайтыныңызды білмейсіз.

**3. Функционалдық емес талаптарды ұмыту.** Сенімділік, қауіпсіздік, платформа бағдарламаның пайдаланушыда шынымен жұмыс істей алатынын анықтайды.

**4. Тексерілмейтін қабылдау критерийлері.** «Нәтиже әдемі көрсетіледі» → «Нәтиже 14 pt шрифтпен, дұрыс жауаптар жасыл, қателер қызыл түспен көрсетіледі».

**5. Тым көп user story.** 30 user story — бұл MVP емес. Must — 4–7 шамасында болғаны дұрыс.

## Ескерту

- ТТ-ны репозиторийде Markdown пішімінде (`docs/tz.md`) сақтаған ыңғайлы: талаптардың өзгерістері код өзгерістері сияқты Git тарихында көрінеді.
- Python нұсқасына қойылатын функционалдық емес талапты кодта бірден тексерген дұрыс: мысалы, `main.py` басында — `import sys; assert sys.version_info >= (3, 10)` немесе `pyproject.toml` ішінде `requires-python = ">=3.10"` көрсету.
- Өнімділік талаптары («1 секундтан аз») өлшеу арқылы тексеріледі: `timeit` модулі немесе амалдың алдында және кейін `time.perf_counter()`.
- Given — When — Then пішіміндегі қабылдау критерийлері AAA тест үлгісіне (Arrange — Act — Assert) тікелей сәйкес келеді.
- Бағдарлама `=` бар f-жолдарды (`f"{x=}"`, Python 3.8+) немесе `match` (Python 3.10+) қолданса, функционалдық емес талаптарда Python-ның ең төменгі нұсқасын көрсетіңіз.
- Құжаттама: [timeit](https://docs.python.org/3/library/timeit.html), [Writing your pyproject.toml](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/).
