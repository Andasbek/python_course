## 1. Что такое техническое задание

**Техническое задание (ТЗ)** — документ, описывающий требования к создаваемой программе, её возможности, ограничения и условия приёмки.

**Зачем оно нужно:**
- **Что мы делаем** и, что важно, **чего мы не делаем** — граница масштаба;
- разбиение работы на этапы и планирование времени;
- основа для проектирования архитектуры и базы данных;
- для тестирования — точное определение того, что значит «работает правильно»;
- при сдаче проекта — ответ на вопрос «сколько из запланированного выполнено».

В реальном производстве ТЗ может занимать десятки страниц (и в Казахстане, и в СНГ есть стандарт ГОСТ 34). Для небольшого проекта достаточно упрощённой версии на **3–5 страниц**.

## 2. Структура ТЗ

| № | Раздел | Содержание |
|---|---|---|
| 1 | Общие сведения | Название проекта, автор, сроки, версия |
| 2 | Цель и проблема | Какую проблему решает, для кого (из карточки идеи) |
| 3 | Пользователи | Типы (роли) пользователей и их цели |
| 4 | Функциональные требования | **Что делает** программа — user story с приоритетом MoSCoW |
| 5 | Нефункциональные требования | **Какой** должна быть программа: скорость, надёжность, удобство, безопасность, платформа |
| 6 | Данные | Какие данные хранятся, откуда поступают, объём |
| 7 | Интерфейс | Список основных окон/экранов (эскиз интерфейса) |
| 8 | Технологии | Язык, библиотеки, база данных, инструменты |
| 9 | Ограничения и допущения | Чего мы не делаем; что предполагаем (например, «есть интернет») |
| 10 | Этапы | Основные этапы и сроки |
| 11 | Критерии приёмки | Когда проект считается «готовым» |

## 3. Функциональные и нефункциональные требования

| | Функциональные | Нефункциональные |
|---|---|---|
| Вопрос | **Что делает** программа? | **Как / какой** работает программа? |
| Пример | «Пользователь может выбрать тему теста» | «График результатов открывается менее чем за 2 секунды» |
| Пример | «Программа сохраняет результат в базу данных» | «Программа работает в Windows 10/11 и Linux» |
| Пример | «Результаты можно экспортировать в CSV» | «Пароль хранится в виде хеша» |
| Пример | | «Интерфейс на казахском языке, шрифт не менее 12 pt» |

**Виды нефункциональных требований:** производительность (скорость, объём), надёжность (не падать при неверном вводе, не терять данные), удобство (язык, понятность, доступность), безопасность (секреты, пароли, ввод), переносимость (ОС, версия Python), сопровождаемость (качество кода, тесты, документация).

## 4. Признаки хорошего требования

Требование должно быть **конкретным**, **проверяемым**, **однозначным**.

| Плохое требование | Почему плохое | Хорошее требование |
|---|---|---|
| «Программа должна быть удобной» | Невозможно проверить | «Любое основное действие доступно из главного окна не более чем за 2 нажатия» |
| «Программа работает быстро» | «Быстро» — насколько? | «Поиск по 1000 записям — менее 1 секунды» |
| «Показывается статистика» | Какая? Как? | «Пользователь может посмотреть столбчатую диаграмму процента правильных ответов по темам» |
| «Данные сохраняются» | Где? Когда? | «По окончании каждого теста результат (дата, тема, балл) автоматически сохраняется в базу SQLite» |
| «Ошибок быть не должно» | Невозможно | «Если в поле для числа ввести текст, программа не падает, а показывает окно с предупреждением» |

**Проверка «Как?»:** прочитайте требование и спросите: «как я это проверю?». Если ответа нет — требование размыто.

## 5. Пользовательская история (user story)

Устоявшаяся форма записи требований с точки зрения пользователя:

```text
Как [РОЛЬ], я хочу [ДЕЙСТВИЕ], чтобы [ЦЕЛЬ / ПОЛЬЗА].
```

Примеры («Тренажёр ЕНТ»):
- US-1. *Как ученик, я хочу выбрать тему и пройти тест из 10 вопросов, чтобы проверить себя по этой теме.*
- US-2. *Как ученик, я хочу по окончании теста видеть свои правильные и неправильные ответы, чтобы учиться на своих ошибках.*
- US-3. *Как ученик, я хочу видеть график своих результатов по темам, чтобы знать свои слабые темы.*
- US-4. *Как преподаватель, я хочу загружать вопросы из CSV-файла, потому что вводить вопросы по одному долго.*

**Почему важно «чтобы/потому что»?** Эта часть объясняет, **зачем** нужна возможность, и помогает найти другое, более простое решение.

### Критерии приёмки

Для каждой user story записываются конкретные условия, при которых она считается «готовой». Удобный формат — **«Дано — Действие — Результат»** (Given — When — Then):

```text
US-2. Просмотр результата теста
  Критерии приёмки:
  1. Дано: ученик ответил на 10 вопросов.
     Действие: нажимает кнопку «Завершить».
     Результат: показывается надпись вида «Результат: 7/10 (70%)».
  2. В окне результата для каждого неправильного ответа показываются вопрос, ответ ученика и правильный ответ.
  3. Результат сохраняется в базу данных с датой и темой.
  4. Если не дано ни одного ответа, кнопка «Завершить» показывает предупреждение «Ответьте хотя бы на один вопрос».
```

Критерии приёмки потом легко превращаются в **тесты** (`unittest`):

```python
import unittest


def natije_matini(dures, barlygy):
    """Возвращает результат теста в виде «7/10 (70%)»."""
    if barlygy == 0:
        raise ValueError("Количество вопросов не должно быть 0")
    return f"{dures}/{barlygy} ({dures * 100 // barlygy}%)"


class TestUS2(unittest.TestCase):
    """Пункт 1 критериев приёмки US-2."""

    def test_natije_matini(self):
        self.assertEqual(natije_matini(7, 10), "7/10 (70%)")

    def test_nol_suraq(self):
        with self.assertRaises(ValueError):
            natije_matini(0, 0)


if __name__ == "__main__":
    unittest.main()
```

## 6. Приоритеты: метод MoSCoW

Если считать все идеи одинаково важными, ничего не будет доведено до конца. Метод **MoSCoW** делит возможности на 4 группы:

| Группа | Значение | Доля (примерно) | Пример (тренажёр ЕНТ) |
|---|---|---|---|
| **M**ust have — обязательно | Без этого проект бессмыслен; MVP | ≈ 60% времени | Прохождение теста, результат, сохранение, график |
| **S**hould have — важно | Очень полезно, но работает и без этого | ≈ 20% | Импорт из CSV, повторение неправильных ответов |
| **C**ould have — хорошо бы | Если останется время | ≈ 20% | Таймер, тёмная тема, звук |
| **W**on't have (this time) — не в этот раз | Сознательно исключено из плана | 0% | Онлайн-рейтинг, мобильная версия |

Список «Won't have» — важный раздел, защищающий масштаб: если спросят «Почему нет мобильной версии?», вы ответите: «Это сознательно исключено в ТЗ, будет в следующей версии».

## 7. Пример: фрагмент ТЗ

```markdown
# Техническое задание: «Тренажёр ЕНТ»
Версия 1.0 · Автор: Әлия С., 10А · Дата: 12.04.2027

## 2. Цель
Помочь ученикам 9–11 классов проходить тематические тесты по разделу
ЕНТ «Математическая грамотность» и определять свои слабые темы.

## 3. Пользователи
| Роль | Цель |
|---|---|
| Ученик | Проходить тесты, смотреть свои результаты |
| Преподаватель (администратор) | Заполнять базу вопросов |

## 4. Функциональные требования
| ID | User story | Приоритет |
|---|---|---|
| US-1 | Как ученик, я хочу выбрать тему и пройти тест из 10 вопросов, ... | Must |
| US-2 | ... видеть свой результат и свои ошибки, ... | Must |
| US-3 | ... видеть график результатов по темам, ... | Must |
| US-4 | Как преподаватель, я хочу загружать вопросы из CSV, ... | Should |
| US-5 | ... ограничить время теста (таймер) ... | Could |
| — | Онлайн-рейтинг, мобильная версия | Won't |

## 5. Нефункциональные требования
- NFR-1. Python 3.10+, Windows 10/11 и Linux.
- NFR-2. Язык интерфейса — казахский.
- NFR-3. При неверном вводе программа не падает, показывает предупреждение.
- NFR-4. При 500 вопросах тест загружается менее чем за 1 секунду.
- NFR-5. Не менее 10 модульных тестов для основной логики; все проходят.

## 9. Ограничения
- Работает на одном компьютере, без интернета.
- Только вопросы с одним правильным ответом (4 варианта).

## 11. Критерии приёмки
- Все требования Must выполнены, их критерии приёмки проверены.
- `python main.py` запускается в чистом venv после установки `requirements.txt`.
- Есть README и руководство пользователя.
```

## 8. Изменение ТЗ

ТЗ — не документ, «высеченный в камне». Если в ходе разработки что-то меняется (возможность оказалась слишком сложной, пришла новая идея), мы **обновляем** ТЗ, повышаем версию (1.0 → 1.1) и записываем это в конце в раздел «История изменений». Главное — вносить изменения **осознанно**, а не «само собой».

## Частые ошибки

**1. Писать в ТЗ «как», а не «что».** «В окне `Toplevel` будет `Listbox`» — это реализация (архитектура, интерфейс). В ТЗ: «Пользователь может увидеть список всех тем и выбрать одну».

**2. Только Must.** Если всё «обязательно» — приоритетов нет; когда не хватит времени, вы не будете знать, что убрать.

**3. Забыть нефункциональные требования.** Надёжность, безопасность, платформа определяют, сможет ли программа реально работать у пользователя.

**4. Непроверяемые критерии приёмки.** «Результат красиво отображается» → «Результат показывается шрифтом 14 pt, правильные ответы — зелёным, ошибки — красным цветом».

**5. Слишком много user story.** 30 user story — это не MVP. Must должно быть примерно 4–7.

## Основные понятия

| Понятие | Объяснение |
|---|---|
| Техническое задание (ТЗ) | Документ с требованиями к программе |
| Функциональное требование | Что делает программа |
| Нефункциональное требование | Какая программа: скорость, надёжность, безопасность, платформа |
| User story | «Как [роль], я хочу [действие], чтобы [цель]» |
| Критерий приёмки | Конкретное, проверяемое условие, при котором требование считается выполненным |
| Given — When — Then | Формат «Дано — Действие — Результат» |
| MoSCoW | Метод приоритизации Must / Should / Could / Won't |
| Масштаб (scope) | Граница того, что входит и что не входит в проект |

## Примечание

- ТЗ удобно хранить в репозитории в формате Markdown (`docs/tz.md`): изменения требований видны в истории Git так же, как изменения кода.
- Нефункциональное требование к версии Python лучше сразу проверять в коде: например, в начале `main.py` — `import sys; assert sys.version_info >= (3, 10)` или указать `requires-python = ">=3.10"` в `pyproject.toml`.
- Требования к производительности («менее 1 секунды») проверяются измерением: модуль `timeit` или `time.perf_counter()` до и после операции.
- Критерии приёмки в формате Given — When — Then напрямую соответствуют шаблону теста AAA (Arrange — Act — Assert).
- Если программа использует f-строки с `=` (`f"{x=}"`, Python 3.8+) или `match` (Python 3.10+), укажите минимальную версию Python в нефункциональных требованиях.
- Документация: [timeit](https://docs.python.org/3/library/timeit.html), [Writing your pyproject.toml](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/).
