## 1. Структура репозитория проекта

Рекомендуемая структура, общая для всех проектов (на примере «Карманных денег»):

```text
qalta-aqshasy/
├── .gitignore            # файлы, которые Git не отслеживает
├── README.md             # описание проекта
├── requirements.txt      # список зависимостей
├── main.py               # точка запуска
├── qalta/                # основной код (пакет)
│   ├── __init__.py
│   ├── models.py         # классы: Operation, Category
│   ├── database.py       # работа с SQLite
│   ├── logic.py          # вычисления, бизнес-логика
│   ├── currency.py       # курс валют через API
│   └── gui.py            # интерфейс Tkinter
├── tests/                # тесты unittest
│   └── test_logic.py
├── data/                 # образцы данных (не настоящая БД!)
│   └── sample.csv
└── docs/                 # ТЗ, ER-диаграмма, изображения прототипа
    ├── tz.md
    ├── data_model.md
    └── prototype.png
```

В игровом проекте вместо `qalta/` будут папки `game/` (sprites.py, levels.py, scenes.py) и `assets/` (images, sounds).

**Почему такая структура?**
- Любой человек при открытии проекта сразу понимает: где код, где тесты, где документация.
- `main.py` короткий: он только запускает приложение. Логика — в модулях, её легко тестировать.

## 2. Пошаговое создание репозитория

### 2.1. Папка, виртуальное окружение, Git
```bash
mkdir qalta-aqshasy
cd qalta-aqshasy
python -m venv venv
# Windows:
venv\Scripts\activate
# macOS / Linux:
source venv/bin/activate
pip install requests matplotlib
pip freeze > requirements.txt
git init
```

### 2.2. `.gitignore`
```text
# Python
__pycache__/
*.pyc

# Виртуальное окружение
venv/
.venv/

# Секретные данные
.env
config_secret.json

# Личная база данных пользователя
*.db

# Файлы редактора и ОС
.vscode/
.idea/

Thumbs.db
```

> **Почему не загружаем `*.db`?** База данных — это личные данные пользователя и к тому же двоичный файл (Git не может показать её изменения). Вместо этого программа при запуске сама создаёт таблицы (функция вроде `create_db()`), а образцы данных хранятся в `data/sample.csv`.

### 2.4. Первый коммит и GitHub
```bash
git add .
git status
git commit -m "Каркас проекта: структура, .gitignore, README, прототип"
git branch -M main
git remote add origin https://github.com/<логин>/qalta-aqshasy.git
git push -u origin main
```

В выводе `git status` файлы `venv/` и `.db` **не должны отображаться** — это значит, что `.gitignore` работает правильно.

### 2.5. Правила сообщений коммитов
| Плохо | Хорошо |
|---|---|
| `update` | `Форма добавления операции: проверка суммы` |
| `fix` | `Исправление: падение программы при пустой категории` |
| `asdf` | `Тест: 3 теста для функции balance()` |
| `всё готово` (работа за 2 недели в одном коммите) | 2–5 небольших коммитов каждый день |

Правило: **один коммит — одно логическое изменение**; сообщение отвечает на вопрос «что сделано».

## 3. Разделение проекта на этапы (декомпозиция)

**Декомпозиция** — разделение большой задачи на мелкие, конкретные, проверяемые части. Слона целиком не съешь — его едят по кусочкам.

Три уровня:
```text
Проект
 └── Этап (эпик): «Работа с данными»
      └── Задача: «database.py: функция add_operation()»
           └── Критерий проверки: «Новая операция появляется в таблице»
```

**Признаки хорошей задачи** (похоже на SMART):
- **Конкретная:** не «Сделать интерфейс» → а «Окно добавления операции: поля суммы, категории, даты».
- **Проверяемая:** как я узнаю, что она готова?
- **Небольшая:** от 30 минут до 2 часов. Если дольше — разделите.
- **Со сроком:** к какой дате будет завершена.

## 4. MVP и метод MoSCoW

**MVP (Minimum Viable Product, минимально жизнеспособный продукт)** — самая простая работающая версия, решающая основную проблему. Сначала доводим до конца MVP, дополнительные возможности — потом.

**MoSCoW** — разделение возможностей на четыре группы:

| Группа | Значение | Пример «Карманных денег» |
|---|---|---|
| **M**ust (обязательно) | без этого проект не работает | добавление операции, сохранение в БД, баланс, история |
| **S**hould (нужно) | важно, но можно и без этого | диаграмма по категориям, экспорт в CSV |
| **C**ould (было бы хорошо) | если останется время | перевод в доллары (API), ночной режим |
| **W**on't (не в этот раз) | в следующую версию | мобильное приложение, несколько пользователей |

> **Правило:** список Must не должен превышать 60% всей работы. Иначе риск слишком высок.

## 5. Установка сроков: контрольные точки (milestones)

Этапы выстраиваются в типичную последовательность; каждому назначается дата и проверяемый результат:

| № | Этап | Результат (milestone) |
|---|---|---|
| 1 | Репозиторий, план | каркас на GitHub + Kanban-доска |
| 2 | Основная логика (1) | основные классы и функции, работает в консоли |
| 3 | Основная логика (2) | сложные алгоритмы, особые случаи |
| 4 | Работа с данными | SQLite/JSON/CSV/API полностью подключены |
| 5 | Интерфейс | интерфейс Tkinter/Pygame объединён с логикой → **MVP** |
| 6 | Промежуточный просмотр | замечания code review записаны в Issues |
| 7 | Тестирование | unittest + ручное тестирование, ошибки исправлены |
| 8 | Доработка | возможности Should/Could, оформление |
| 9 | Документирование | README, руководство пользователя |
| 10 | Публикация | релиз v1.0 |

О **буфере**: закладывайте на каждый этап в 1,5 раза больше времени и планируйте завершить работу раньше крайнего срока — оставшееся время уйдёт на непредвиденные ошибки.

## 6. Планирование с помощью инструментов GitHub

| Инструмент | Для чего | Как |
|---|---|---|
| **Issues** | каждая задача или ошибка — один issue | Issues → New issue; название + описание + критерий проверки |
| **Labels** (метки) | обозначить тип | `must`, `should`, `could`, `bug`, `docs` |
| **Milestones** (этапы) | сгруппировать issues по этапам, поставить срок | Issues → Milestones → «MVP (29.04)», «v1.0 (11.05)» |
| **Projects** (Kanban-доска) | видеть прогресс | столбцы: *В плане → В работе → На проверке → Готово* |

Образец описания issue (используется список задач в markdown):
```text
Название: Окно добавления операции

Что нужно сделать:
- [ ] поля суммы, категории, даты, комментария
- [ ] проверка суммы (целое положительное число)
- [ ] «Сохранить» -> database.add_operation()

Считается готовым, если: новая операция появляется в таблице и влияет на баланс.
Этап: MVP (29.04) · Метка: must
```

Если указать номер issue в коммите, GitHub их свяжет: `git commit -m "Окно добавления операции (#7)"`. А если написать `Closes #7`, issue автоматически закроется, когда коммит попадёт в `main`.

> Если GitHub недоступен, ту же доску можно вести в файле `docs/plan.md` в виде таблицы markdown или с помощью бумажных стикеров.

## 7. Контроль плана с помощью Python (дополнительно)

Небольшой скрипт, который хранит список задач в `docs/plan.csv` и считает прогресс, — применение модуля `csv`:

```python
import csv
import io

# В настоящем проекте: open("docs/plan.csv", encoding="utf-8")
PLAN = """task,stage,deadline,status
models.py классы,2,22.04,done
logic.py баланс,2,22.04,done
logic.py месячный отчёт,3,26.04,doing
database.py CRUD,4,27.04,todo
gui.py главное окно,5,29.04,todo
"""

rows = list(csv.DictReader(io.StringIO(PLAN)))
done = sum(1 for r in rows if r["status"] == "done")
percent = done * 100 // len(rows)
print(f"Выполнено: {done}/{len(rows)} ({percent}%)")
print("[" + "#" * (percent // 10) + "-" * (10 - percent // 10) + "]")
for r in rows:
    if r["status"] != "done":
        print(f"  до {r['deadline']}: {r['task']} ({r['status']})")
```

Результат:
```text
Выполнено: 2/5 (40%)
[####------]
  до 26.04: logic.py месячный отчёт (doing)
  до 27.04: database.py CRUD (todo)
  до 29.04: gui.py главное окно (todo)
```

## 8. Заранее продумать риски

| Риск | Признак | Что делаем |
|---|---|---|
| Новая библиотека оказалась сложнее, чем ожидалось | на одну задачу ушло вдвое больше времени | чтение документации, вопрос более опытному разработчику, более простая альтернатива |
| API перестал работать | нет интернета / ошибка сервера | хранить последний ответ в кэше, офлайн-режим |
| Компьютер сломался / файл потерян | — | **`git push` в конце каждого рабочего дня** |
| Нет возможности работать несколько дней | отставание от плана | буферное время, работа с любого компьютера (репозиторий на GitHub) |
| Слишком много возможностей | длинный список Must | пересмотреть MoSCoW |

## Частые ошибки

**1. Загрузить папку `venv` на GitHub.** Репозиторий заполняется тысячами файлов. Исправление:
```bash
echo venv/ >> .gitignore
git rm -r --cached venv
git commit -m "Удаление папки venv из репозитория"
```

**2. Создать `.gitignore` после добавления файлов.** Git не начнёт игнорировать файлы, которые уже отслеживались, — нужен `git rm --cached`, как показано выше.

**3. Закоммитить файл с паролем или API-ключом.** Даже если потом удалить, он останется в истории. Нужно заменить ключ на новый и впредь использовать `.env` + `.gitignore`.

**4. Слишком большая задача.** «Сделать игру» — это не задача, а весь проект. Разделите: «Персонаж движется влево-вправо», «Столкновение с препятствием», «Счётчик очков».

**5. Забыть обновить `requirements.txt`.** После каждой установки новой библиотеки — `pip freeze > requirements.txt`. Иначе на другом компьютере появится `ModuleNotFoundError`.

**6. Весь код в `main.py` (500 строк).** Разделите на модули по слоям архитектуры (данные, логика, интерфейс).

## Основные понятия
| Понятие | Объяснение |
|---|---|
| Репозиторий | хранилище файлов проекта и истории их изменений |
| `.gitignore` | список файлов, которые Git не отслеживает |
| `requirements.txt` | необходимые проекту библиотеки и их версии |
| Декомпозиция | разделение большой задачи на мелкие задачи |
| MVP | самая простая работающая версия, решающая основную проблему |
| MoSCoW | метод приоритизации Must / Should / Could / Won't |
| Milestone | контрольная точка (этап) со сроком |
| Issue | запись задачи или ошибки на GitHub |
| Kanban-доска | доска, показывающая состояние задач по столбцам |
| Диаграмма Ганта | таблица расположения задач во времени |

## Примечание

- `pip freeze` записывает **все** пакеты окружения, включая зависимости зависимостей; для небольшого проекта можно вручную оставить в `requirements.txt` только прямые зависимости с версиями (`requests>=2.31`).
- Имя виртуального окружения `.venv` распознают VS Code и PyCharm автоматически; с Python 3.13 `venv` сам создаёт внутри папки окружения файл `.gitignore`.
- Начиная с Git 2.28 ветку по умолчанию можно задать один раз: `git config --global init.defaultBranch main` — тогда не нужен `git branch -M main`.
- Имя пакета (папки с `__init__.py`) пишите строчными буквами без дефисов (`qalta`, а не `qalta-aqshasy`) — по PEP 8 и чтобы работал `import`.
- Шаблоны `.gitignore` для Python: https://github.com/github/gitignore/blob/main/Python.gitignore; документация venv: https://docs.python.org/3/library/venv.html
