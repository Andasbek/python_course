## 1. Что такое модель данных?

**Модель данных (data model)** — схема, описывающая, какую информацию хранит программа, на какие части эта информация делится и как части связаны друг с другом.

Модель отвечает на три вопроса:

| Вопрос | Понятие | Пример (проект «Карманные деньги») |
|---|---|---|
| Что храним? | **Сущность** (entity) | Пользователь, Категория, Операция |
| Какие у неё свойства? | **Атрибут** (attribute) | Сумма, дата, комментарий операции |
| Как они связаны? | **Связь** (relationship) | В одной категории много операций |

Сквозной пример в этой теме — проект «Карманные деньги» (приложение на Tkinter + SQLite + Matplotlib + API, которое учитывает доходы и расходы). Те же шаги применимы к любому проекту.

## 2. Поиск сущностей в тексте ТЗ

Простой приём — **метод существительных и глаголов**:
- **существительные** в ТЗ → кандидаты в сущности или атрибуты;
- **глаголы** → кандидаты в связи или действия (функции).

Фрагмент ТЗ:
> «Пользователь вводит свои **доходы** и **расходы**. У каждой **операции** есть **сумма**, **дата**, **категория** (еда, транспорт, развлечения) и **комментарий**. Пользователь может установить месячный **лимит**. Программа показывает суммы в долларах по **курсу валют**.»

Сортируем существительные:

| Существительное | Решение | Причина |
|---|---|---|
| Пользователь | **Сущность** | есть собственные атрибуты (имя, логин) |
| Операция | **Сущность** | основная хранимая информация |
| Категория | **Сущность** | общая для нескольких операций, есть своё название и цвет |
| Сумма, дата, комментарий | Атрибут | свойства одной сущности |
| Доход/расход | Атрибут (`kind`) | лишь вид операции |
| Лимит | Атрибут или сущность | если ставится на одну категорию на один месяц — отдельная таблица `budget` |
| Курс валют | **Не хранится** | получаем из API, можно хранить только как кэш |

> **Правило:** если какая-то информация **повторяется** в нескольких записях и у неё есть собственные свойства — она заслуживает быть отдельной сущностью (таблицей).

## 3. Атрибуты и типы данных

В SQLite основных типов немного, но правильный выбор важен:

| Тип SQLite | Тип Python | Что хранится | Пример |
|---|---|---|---|
| `INTEGER` | `int` | целое число, id, логическое 0/1 | `id`, `amount` (в тенге) |
| `REAL` | `float` | дробное число | средняя оценка, координата |
| `TEXT` | `str` | текст, дата (в формате ISO) | `'2027-04-15'`, `'Еда'` |
| `BLOB` | `bytes` | двоичные данные | изображение (используется редко) |

Советы:
- **Деньги** лучше хранить в тиынах или тенге как `INTEGER`: не будет дробных ошибок вроде `0.1 + 0.2`.
- **Дату** храните как `TEXT` в формате `ГГГГ-ММ-ДД`: тогда `ORDER BY date` сортирует правильно.
- Атрибут должен быть **атомарным**: не «ФИО», а `first_name` и `last_name`; даже если «Адрес» умещается в одну строку, но нужен фильтр по городу — `city` должно быть отдельным полем.

## 4. Ключи и ограничения (constraints)

| Ограничение | Значение | Пример |
|---|---|---|
| `PRIMARY KEY` | уникальный номер записи | `id INTEGER PRIMARY KEY AUTOINCREMENT` |
| `FOREIGN KEY` | ссылка на запись другой таблицы | `category_id REFERENCES category(id)` |
| `NOT NULL` | не должно быть пустым | `amount INTEGER NOT NULL` |
| `UNIQUE` | не должно повторяться | `login TEXT UNIQUE` |
| `CHECK` | условие на значение | `CHECK (amount > 0)` |
| `DEFAULT` | значение по умолчанию | `created TEXT DEFAULT CURRENT_TIMESTAMP` |

Бывают **естественный ключ** (ИИН, логин) и **искусственный ключ** (`id`). В проекте всегда используйте искусственный `id`: естественное значение может измениться (пользователь сменит логин), а `id` не меняется никогда.

> **Важно:** в SQLite внешние ключи по умолчанию **не проверяются**. При каждом подключении нужно выполнять `PRAGMA foreign_keys = ON;`.

## 5. Типы связей

| Тип | Значение | Пример из жизни | Как реализуется |
|---|---|---|---|
| **1:1** (один к одному) | одной записи A соответствует только одна запись B | Ученик ↔ Ученический билет | `UNIQUE` внешний ключ в таблице B (или объединение в одну таблицу) |
| **1:N** (один ко многим) | одной записи A соответствует много записей B | Класс → Ученики; Категория → Операции | Добавляем внешний ключ в таблицу на стороне «много» |
| **N:M** (многие ко многим) | много с обеих сторон | Ученики ↔ Кружки | **Промежуточная таблица** (junction table) с двумя внешними ключами |

### Решение связи N:M через промежуточную таблицу
Один ученик ходит в несколько кружков, в одном кружке много учеников. Добавить в таблицу учеников столбцы `club1, club2, club3` — **ошибка** (мы не знаем, сколько будет кружков). Правильно:

```text
student            enrollment                 club
--------           -------------------        --------
id  (PK)  <───┐    student_id (FK) ──┘        id (PK)
name          └──  club_id    (FK) ────────>  title
                   joined_date
                   PRIMARY KEY (student_id, club_id)
```

В промежуточной таблице могут быть и собственные атрибуты связи (`joined_date` — когда записался).

## 6. ER-диаграмма (Entity–Relationship)

ER-диаграмма — рисунок, на котором сущности показаны прямоугольниками, а связи — линиями. Её можно нарисовать на бумаге или в draw.io. В текстовом виде (1 и N вместо значка «воронья лапка»):

```text
┌──────────────┐ 1        N ┌───────────────────┐ N        1 ┌──────────────┐
│    user      │────────────│    operation      │────────────│   category   │
├──────────────┤            ├───────────────────┤            ├──────────────┤
│ id   PK      │            │ id          PK    │            │ id    PK     │
│ name         │            │ user_id     FK    │            │ title UNIQUE │
│ login UNIQUE │            │ category_id FK    │            │ kind         │
└──────────────┘            │ amount            │            │ color        │
        │ 1                 │ op_date           │            └──────────────┘
        │                   │ note              │                   │ 1
        │ N                 └───────────────────┘                   │
┌──────────────────────┐                                            │
│       budget         │ N ─────────────────────────────────────────┘
├──────────────────────┤
│ id PK, user_id FK,   │
│ category_id FK,      │
│ month, limit_amount  │
└──────────────────────┘
```

Читается так: «У одного пользователя много операций», «К одной категории относится много операций», «Каждый пользователь ставит один лимит на каждую категорию на каждый месяц».

## 7. Нормализация — простым языком

Посмотрите на пример «записали всё в одну таблицу»:

| op_id | user_name | user_login | category | category_color | amount | date |
|---|---|---|---|---|---|---|
| 1 | Айгерим | aigerim | Еда, Транспорт | зелёный | 1500 | 2027-04-01 |
| 2 | Айгерим | aigerim | Еда | зелёный | 800 | 2027-04-02 |
| 3 | Айгерим | aigerim | Игры | красный | 2000 | 2027-04-03 |

Проблемы (аномалии):
- **Повторение:** «Айгерим, aigerim» записано в каждой строке — память расходуется впустую.
- **Аномалия обновления:** если изменить цвет категории «Еда», нужно менять все строки; забудем одну — данные противоречат друг другу.
- **Аномалия удаления:** если удалить 3-ю строку, информация о категории «Игры» полностью пропадёт.
- **Неатомарное значение:** «Еда, Транспорт» — два значения в одной ячейке.

Три основных правила:

| Нормальная форма | Краткое правило | Исправление |
|---|---|---|
| **1НФ** | В каждой ячейке только одно значение, нет повторяющихся групп (`club1, club2`) | «Еда, Транспорт» → две отдельные строки или промежуточная таблица |
| **2НФ** | Неключевое поле зависит от **всего** ключа (если ключ составной) | в промежуточной таблице не храним имя ученика |
| **3НФ** | Неключевое поле зависит только от ключа, а не от другого неключевого поля | `category_color` зависит от категории → переносим в таблицу `category` |

> **Чтобы запомнить:** «Каждое данное хранится один раз и на своём месте».

**Исключение (денормализация):** иногда ради скорости вычислений данные намеренно дублируют (например, хранят итоговую сумму). В небольшом проекте это обычно не нужно — сначала доведите модель до 3НФ.

## 8. Словарь данных (data dictionary)

Словарь данных — документ-таблица о каждом поле каждой таблицы. Он записывается в README или в файл `docs/data_model.md` и служит частью документации проекта.

**Таблица `operation`:**

| Поле | Тип | Ограничение | Описание |
|---|---|---|---|
| `id` | INTEGER | PK, AUTOINCREMENT | номер операции |
| `user_id` | INTEGER | FK → user.id, NOT NULL | чья операция |
| `category_id` | INTEGER | FK → category.id, NOT NULL | категория |
| `amount` | INTEGER | NOT NULL, CHECK > 0 | сумма, тенге |
| `op_date` | TEXT | NOT NULL | дата, `ГГГГ-ММ-ДД` |
| `note` | TEXT | — | комментарий (необязательно) |

## 9. Превращение модели в схему SQLite

Схему храним в отдельном файле `schema.sql` или внутри Python. `executescript()` выполняет сразу несколько SQL-инструкций.

```python
import sqlite3

SCHEMA = """
CREATE TABLE IF NOT EXISTS user (
    id    INTEGER PRIMARY KEY AUTOINCREMENT,
    name  TEXT NOT NULL,
    login TEXT NOT NULL UNIQUE
);

CREATE TABLE IF NOT EXISTS category (
    id    INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL UNIQUE,
    kind  TEXT NOT NULL CHECK (kind IN ('доход', 'расход')),
    color TEXT DEFAULT '#888888'
);

CREATE TABLE IF NOT EXISTS operation (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id     INTEGER NOT NULL REFERENCES user(id) ON DELETE CASCADE,
    category_id INTEGER NOT NULL REFERENCES category(id),
    amount      INTEGER NOT NULL CHECK (amount > 0),
    op_date     TEXT NOT NULL,
    note        TEXT
);

CREATE TABLE IF NOT EXISTS budget (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id      INTEGER NOT NULL REFERENCES user(id) ON DELETE CASCADE,
    category_id  INTEGER NOT NULL REFERENCES category(id),
    month        TEXT NOT NULL,
    limit_amount INTEGER NOT NULL CHECK (limit_amount > 0),
    UNIQUE (user_id, category_id, month)
);
"""


def create_db(path="qalta.db"):
    """Создаёт базу данных и таблицы."""
    conn = sqlite3.connect(path)
    conn.execute("PRAGMA foreign_keys = ON;")
    conn.executescript(SCHEMA)
    conn.commit()
    return conn


if __name__ == "__main__":
    conn = create_db(":memory:")
    tables = conn.execute(
        "SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%'"
    ).fetchall()
    print("Созданные таблицы:", [t[0] for t in tables])
    conn.close()
```

Результат:
```text
Созданные таблицы: ['user', 'category', 'operation', 'budget']
```

`ON DELETE CASCADE` — если пользователь удалён, все его операции тоже автоматически удаляются. `UNIQUE (user_id, category_id, month)` — нельзя поставить два лимита на одну категорию в одном месяце.

### Проверка модели: напишем запрос
Правильна ли модель — проверяем, отвечая с помощью SQL на основные вопросы из ТЗ. Например: «Сколько потрачено на каждую категорию в апреле?»

```python
import sqlite3

conn = sqlite3.connect(":memory:")
conn.executescript("""
CREATE TABLE category (id INTEGER PRIMARY KEY, title TEXT, kind TEXT);
CREATE TABLE operation (id INTEGER PRIMARY KEY, category_id INTEGER,
                        amount INTEGER, op_date TEXT);
INSERT INTO category VALUES (1, 'Еда', 'расход'), (2, 'Транспорт', 'расход');
INSERT INTO operation (category_id, amount, op_date) VALUES
    (1, 1500, '2027-04-01'), (1, 800, '2027-04-02'), (2, 200, '2027-04-02');
""")
rows = conn.execute("""
    SELECT c.title, SUM(o.amount)
    FROM operation AS o
    JOIN category AS c ON c.id = o.category_id
    WHERE o.op_date LIKE '2027-04-%'
    GROUP BY c.title
    ORDER BY SUM(o.amount) DESC
""").fetchall()
for title, total in rows:
    print(f"{title}: {total} тг")
```

Результат:
```text
Еда: 2300 тг
Транспорт: 200 тг
```

Если на какой-то вопрос из ТЗ невозможно ответить с помощью модели — в модели чего-то не хватает.

## 10. Связь с классами Python

В многослойной архитектуре каждой сущности соответствует один класс. Одна строка таблицы — один объект:

```python
class Category:
    """Категория: объект, соответствующий одной строке таблицы."""

    def __init__(self, id_, title, kind, color="#888888"):
        self.id = id_
        self.title = title
        self.kind = kind
        self.color = color

    @classmethod
    def from_row(cls, row):
        """Создаёт объект из строки SQL (кортежа)."""
        return cls(*row)

    def __repr__(self):
        return f"Category({self.id}, {self.title!r}, {self.kind!r})"


row = (1, "Еда", "расход", "#2e7d32")
cat = Category.from_row(row)
print(cat)
```

Результат:
```text
Category(1, 'Еда', 'расход')
```

## 11. SQLite, JSON или CSV?

| Ситуация | Выбор |
|---|---|
| Несколько связанных сущностей, много поиска/фильтрации/отчётов | **SQLite** |
| Настройки, небольшой список (таблица рекордов, 10–100 записей) | **JSON** |
| Передача данных в Excel или Pandas | экспорт в **CSV** |
| Данные приходят из API, хранить не нужно | не храним, при необходимости — кэш |

В игровом проекте (Pygame) тоже нужна модель: `player`, `level`, `score` — но они могут храниться в JSON. И всё равно **структуру** проектируем заранее.

```python
import json

# Модель данных игры в виде JSON
save_data = {
    "player": {"name": "Нурлан", "coins": 120},
    "levels": [
        {"number": 1, "best_score": 340, "stars": 3},
        {"number": 2, "best_score": 150, "stars": 1},
    ],
}
text = json.dumps(save_data, ensure_ascii=False, indent=2)
print(text[:60])
```

Результат:
```text
{
  "player": {
    "name": "Нурлан",
    "coins": 120
  },
```

## Частые ошибки

**1. Записывать всё в одну таблицу.**
```text
students(id, name, club1, club2, club3)    -- ошибка: число кружков ограничено, много пустых столбцов
```
Правильно: таблицы `student`, `club` и промежуточная `enrollment(student_id, club_id)`.

**2. Ставить внешний ключ на стороне «один».**
```text
category(id, title, operation_id)          -- ошибка: в категории останется только одна операция
```
Правильно: внешний ключ на стороне «много» — `operation(..., category_id)`.

**3. Забыть включить внешние ключи.**
```python
import sqlite3
conn = sqlite3.connect(":memory:")
# Нет PRAGMA — ссылка на несуществующую категорию не вызывает ошибки!
conn.executescript("""
CREATE TABLE category (id INTEGER PRIMARY KEY, title TEXT);
CREATE TABLE operation (id INTEGER PRIMARY KEY,
                        category_id INTEGER REFERENCES category(id));
INSERT INTO operation (category_id) VALUES (999);
""")
print("Ошибочная запись принята:", conn.execute("SELECT * FROM operation").fetchall())
```
Результат:
```text
Ошибочная запись принята: [(1, 999)]
```
Правильно: сразу после подключения `conn.execute("PRAGMA foreign_keys = ON")` — тогда появится `sqlite3.IntegrityError: FOREIGN KEY constraint failed`.

**4. Хранить вычисляемое значение.** Хранить возраст ученика (`age`) — через год он будет неверным. Храните дату рождения (`birth_date`), а возраст вычисляйте. Точно так же не храните баланс, а вычисляйте его из операций через `SUM`.

**5. Хранить деньги в типе `REAL`.** `0.1 + 0.2 == 0.30000000000000004`. Храните деньги в тенге/тиынах как `INTEGER`.

## Основные понятия
| Понятие | Объяснение |
|---|---|
| Модель данных | схема структуры и связей хранимой информации |
| Сущность (entity) | объект, превращающийся в отдельную таблицу: пользователь, книга, вопрос |
| Атрибут | свойство сущности, поле в таблице |
| Первичный ключ (PK) | уникальный идентификатор записи |
| Внешний ключ (FK) | ссылка на запись в другой таблице |
| Связь 1:N | одной записи соответствует много записей |
| Связь N:M | связь «многие ко многим», реализуемая через промежуточную таблицу |
| ER-диаграмма | рисунок сущностей и связей |
| Нормализация | правила устранения повторов и аномалий (1НФ, 2НФ, 3НФ) |
| Словарь данных | документ, в котором записаны тип, ограничение и описание каждого поля |

## Примечание

- `PRAGMA foreign_keys = ON` действует только на текущее соединение: включайте его в функции, которая открывает подключение, а не один раз «при создании базы».
- `AUTOINCREMENT` в SQLite не обязателен: столбец `INTEGER PRIMARY KEY` и так получает номер автоматически; `AUTOINCREMENT` лишь гарантирует, что номера удалённых записей не будут использованы повторно.
- SQLite использует «гибкую типизацию»: в столбец `INTEGER` можно записать строку. Начиная с SQLite 3.37 можно объявить таблицу `STRICT`, и тогда типы проверяются строго.
- Подставляйте значения в запросы только через параметры `?` (`conn.execute("... WHERE id = ?", (op_id,))`), а не через f-строки — это защищает от SQL-инъекций.
- Имена таблиц и столбцов пишите в `snake_case` и в единственном числе (`operation`, `category_id`) — так же, как имена переменных по PEP 8.
- Документация модуля: https://docs.python.org/3/library/sqlite3.html
