## 1. Три вида ошибок

| Вид | Когда обнаруживается | Пример | Сложность поиска |
|---|---|---|---|
| Синтаксическая (SyntaxError) | До запуска | Забыто двоеточие, не закрыта скобка | Легко — Python сам показывает |
| Ошибка времени выполнения (runtime, exception) | Во время выполнения | Деление на 0, нет ключа, нет файла | Средне — помогает Traceback |
| Логическая | Сама никогда не обнаруживается! | При вычислении среднего делим на число на один меньше | Трудно — программа «работает», но ответ неверный |

Пример логической ошибки:

```python
bagalar = [5, 4, 3, 5]
ortasha = sum(bagalar) / (len(bagalar) - 1)    # ошибка: лишнее -1
print("Среднее:", ortasha)
```

Результат:
```text
Среднее: 5.666666666666667
```

Программа завершилась без ошибок, но средняя оценка не может быть больше 5! Чтобы найти логическую ошибку, нужно **заранее знать ожидаемый результат**.

## 2. Чтение Traceback

```python
def ortasha_ball(ballar):
    return sum(ballar) / len(ballar)


def synyp_esebi(synyptar):
    for atau, ballar in synyptar.items():
        print(atau, ortasha_ball(ballar))


synyp_esebi({"9А": [80, 90], "9Ә": []})
```

Результат:
```text
9А 85.0
Traceback (most recent call last):
  File "esep.py", line 10, in <module>
    synyp_esebi({"9А": [80, 90], "9Ә": []})
  File "esep.py", line 7, in synyp_esebi
    print(atau, ortasha_ball(ballar))
  File "esep.py", line 2, in ortasha_ball
    return sum(ballar) / len(ballar)
ZeroDivisionError: division by zero
```

**Читаем снизу вверх:**
1. **Последняя строка** — тип и описание ошибки: `ZeroDivisionError: division by zero`.
2. **Строка над ней** — место, где ошибка фактически произошла: `line 2, in ortasha_ball`.
3. **Выше** — цепочка вызовов (стек): `<module>` → `synyp_esebi` → `ortasha_ball`. Она показывает, «как ошибка туда добралась».

Вывод: список ballar класса `9Ә` пуст. Исправление — проверить пустой список:

```python
def ortasha_ball(ballar):
    if not ballar:
        return 0
    return sum(ballar) / len(ballar)
```

## 3. Систематический алгоритм поиска ошибок

```text
1. ВОСПРОИЗВЕДИ    →  Добейся стабильного повторения ошибки (на каком вводе?)
2. ЛОКАЛИЗУЙ       →  Найди самый маленький код, вызывающий ошибку (minimal example)
3. ВЫДВИНИ ГИПОТЕЗУ →  «Мне кажется, переменная x здесь равна None»
4. ПРОВЕРЬ         →  Проверь гипотезу через print / logging / debugger
5. ИСПРАВЬ         →  Устрани причину (а не симптом!)
6. ПЕРЕПРОВЕРЬ     →  Ошибка исчезла? Ничего другого не сломалось? (автоматические тесты)
```

**Полезные приёмы:**

- **Деление пополам (бисекция).** Поставить `print` в середину кода из 200 строк и проверить: ошибка до него или после. На каждом шаге область поиска уменьшается вдвое.
- **«Метод утёнка» (rubber duck debugging).** Вслух построчно объясните код игрушке (или другу). В процессе объяснения ошибка обнаруживается сама — это действительно работает!
- **Проверка последнего изменения.** «Вчера работало» — посмотрите, что изменилось, через `git diff` и `git log`.
- **Поиск сообщения об ошибке.** Скопировать последнюю строку целиком в поисковик (или документацию).
- **Проверка данных.** Многие ошибки не в коде, а в данных: пустая строка, лишний пробел, `"5"` (текст) и `5` (число).

### Отладка с `print` (самый простой способ)

```python
def zhenildik_baga(baga, paiyz):
    print(f"DEBUG: baga={baga!r}, paiyz={paiyz!r}")      # !r — показывает и тип
    return baga - baga * paiyz / 100
```

Формат `!r` различает `'500'` (текст) и `500` (число) — очень полезно при поиске ошибок типов.

## 4. Отладчик VS Code (debugger)

Ставить `print` во множество мест, а затем удалять — неудобно. Отладчик может **остановить** программу **на любой строке** и показать все переменные.

**Порядок работы:**
1. Щёлкните слева от номера строки, чтобы поставить **точку останова** (breakpoint, красная точка).
2. `F5` (или «Run → Start Debugging» → «Python File»).
3. Программа приостановится на точке останова. В панели **VARIABLES** слева видны текущие значения всех переменных.
4. Кнопки управления:

| Кнопка | Клавиша | Действие |
|---|---|---|
| Continue | `F5` | Продолжить до следующей точки останова |
| Step Over | `F10` | Перейти к следующей строке (не заходя внутрь функции) |
| Step Into | `F11` | Зайти внутрь вызываемой функции |
| Step Out | `Shift+F11` | Выйти из текущей функции |
| Restart | `Ctrl+Shift+F5` | Начать заново |
| Stop | `Shift+F5` | Остановить |

5. В панели **WATCH** можно записать выражение (например, `len(ballar)`) и следить за его значением.
6. **CALL STACK** — как Traceback, цепочка вызовов.
7. **Условная точка останова:** щёлкните правой кнопкой мыши по красной точке → «Edit Breakpoint» → `i == 57`. Цикл остановится, только когда дойдёт до 57-й итерации.

При работе в терминале встроенная функция `breakpoint()` (Python 3.7+) запускает отладчик `pdb`: `n` — следующая строка, `s` — зайти внутрь, `p x` — вывести переменную, `c` — продолжить, `q` — выйти.

## 5. `assert` — проверь себя

`assert условие, "сообщение"` — если условие ложно, выбрасывает `AssertionError`. Это способ записать в коде предположение «здесь обязательно должно быть так»:

```python
def paiyz(bolik, butin):
    assert butin > 0, "Значение целого должно быть положительным"
    return bolik / butin * 100


print(paiyz(25, 200))
```

Результат:
```text
12.5
```

`assert` **не** для проверки пользовательского ввода (это делаем через `if` + сообщение), а для раннего обнаружения собственных ошибок программиста.

## 6. Модуль `logging`

### Почему `print` недостаточно?

| | `print` | `logging` |
|---|---|---|
| Уровень важности | Нет | 5 уровней |
| Время, файл, номер строки | Вручную | Автоматически |
| Выключить/включить | Нужно удалять каждую строку | Одной строкой (`level=`) |
| Запись в файл | Вручную | `filename=` |
| В реальных проектах | Только временно | Стандарт |

**Лог (журнал)** — «дневник» программы: что произошло, когда, где. Если сервер упал ночью, программист утром читает лог-файл и находит причину.

### Уровни

| Уровень | Число | Когда |
|---|---|---|
| `DEBUG` | 10 | Подробности для отладки (значения переменных) |
| `INFO` | 20 | Обычные события («Файл прочитан: 150 строк») |
| `WARNING` | 30 | Неожиданно, но работа продолжается («Заполнено 3 пропуска») |
| `ERROR` | 40 | Ошибка: одно действие не выполнено («Файл не найден») |
| `CRITICAL` | 50 | Программа не может продолжать работу |

Уровень по умолчанию — `WARNING`: сообщения ниже него (`DEBUG`, `INFO`) не показываются.

### Простой пример

```python
import logging

logging.basicConfig(
    level=logging.DEBUG,
    format="%(asctime)s | %(levelname)-8s | %(message)s",
    datefmt="%H:%M:%S",
)

logging.debug("Программа запущена")
logging.info("Пользователь вошёл: %s", "Әлия")
logging.warning("Слабый пароль")
logging.error("Не удалось подключиться к базе данных")
```

Результат (время будет другим):
```text
10:15:02 | DEBUG    | Программа запущена
10:15:02 | INFO     | Пользователь вошёл: Әлия
10:15:02 | WARNING  | Слабый пароль
10:15:02 | ERROR    | Не удалось подключиться к базе данных
```

Примечание: `basicConfig` вызывается в программе **один раз** и в самом начале. Передача значений через `%s` эффективнее f-строки (если сообщение не выводится, строка не собирается).

### Поля формата

| Поле | Значение |
|---|---|
| `%(asctime)s` | Время |
| `%(levelname)s` | Название уровня |
| `%(message)s` | Сообщение |
| `%(name)s` | Имя логгера |
| `%(filename)s`, `%(lineno)d` | Имя файла, номер строки |
| `%(funcName)s` | Имя функции |

### Запись в файл и собственный логгер

```python
import logging

logging.basicConfig(
    filename="app.log",
    encoding="utf-8",
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(name)s:%(lineno)d — %(message)s",
)
logger = logging.getLogger(__name__)     # собственный логгер модуля


def bolu(a, b):
    logger.debug("Вызвана bolu(%s, %s)", a, b)
    try:
        natije = a / b
    except ZeroDivisionError:
        logger.exception("Попытка деления на ноль: a=%s", a)    # записывает вместе с Traceback
        return None
    logger.info("Результат: %s", natije)
    return natije


bolu(10, 2)
bolu(5, 0)
```

Содержимое файла `app.log` (примерно):
```text
2027-03-29 10:20:11,532 [INFO] __main__:15 — Результат: 5.0
2027-03-29 10:20:11,533 [ERROR] __main__:13 — Попытка деления на ноль: a=5
Traceback (most recent call last):
  File "app.py", line 11, in bolu
    natije = a / b
ZeroDivisionError: division by zero
```

Сообщение `DEBUG` в файл не попало, потому что `level=logging.INFO`. Если при отладке заменить на `level=logging.DEBUG` — будет видно всё. Изменением **одной строки**!

`logger.exception(...)` используется только внутри блока `except` — он пишет с уровнем `ERROR` и добавляет Traceback.

### Правила логирования

- **Никогда** не записывайте в лог секретные данные (пароль, API-ключ, номер карты).
- Сообщение должно быть конкретным: не «Ошибка», а «Файл не найден: data/raw.csv».
- Добавьте файл `app.log` в `.gitignore`.

## Частые ошибки

**1. Чтение Traceback сверху.** Самая важная информация — в двух последних строках.

**2. Исправление симптома.**
```python
try:
    ortasha = sum(ballar) / len(ballar)
except Exception:
    pass                     # ошибка «исчезла», но причина осталась — это ещё опаснее
```
Правильно — устранить причину (проверить пустой список) или перехватить конкретную ошибку и записать в лог:
```python
import logging

ballar = []
if ballar:
    ortasha = sum(ballar) / len(ballar)
else:
    logging.warning("Список баллов пуст — среднее принято равным 0")
    ortasha = 0
```

**3. Поздний вызов `basicConfig`.** Сначала `logging.info(...)`, потом `basicConfig(...)` — настройки не применятся. `basicConfig` — в самом начале.

**4. Не видно `logging.debug`.** Уровень по умолчанию — `WARNING`. Добавьте `level=logging.DEBUG`.

**5. Изменение нескольких вещей одновременно.** Вы внесли три исправления, ошибка исчезла — какое из них помогло? За один раз — одно изменение.

## Основные понятия

| Понятие | Объяснение |
|---|---|
| Баг (bug) | Ошибка в программе |
| Debugging (отладка) | Процесс поиска и устранения ошибки |
| Traceback | Сообщение, показывающее место ошибки и цепочку вызовов |
| Логическая ошибка | Программа работает без ошибок, но результат неверный |
| Точка останова (breakpoint) | Строка, на которой отладчик останавливает программу |
| Step Over / Step Into | Перейти к следующей строке / зайти внутрь функции |
| `assert` | Проверка, выбрасывающая ошибку, если условие ложно |
| Лог (журнал) | Запись событий программы |
| Уровень логирования | Важность сообщения: DEBUG → CRITICAL |

## Примечание

- Начиная с Python 3.11 Traceback подчёркивает знаками `^^^^` точное выражение в строке, где произошла ошибка, а 3.12–3.13 подсказывают возможные опечатки в именах (`Did you mean: 'ballar'?`).
- Python, запущенный с флагом `-O` (`python -O app.py`), **пропускает** все инструкции `assert`, поэтому на них нельзя полагаться для проверки данных.
- `logging.basicConfig()` ничего не делает, если у корневого логгера уже есть обработчики; в Python 3.8+ можно перенастроить его параметром `force=True`.
- В библиотечных модулях используйте `logger = logging.getLogger(__name__)` и не вызывайте `basicConfig` — настройку логирования выполняет главная программа.
- Для больших лог-файлов есть `logging.handlers.RotatingFileHandler`, который ограничивает размер файла и хранит несколько старых копий.
- Документация: [Logging HOWTO](https://docs.python.org/3/howto/logging.html), [pdb — отладчик Python](https://docs.python.org/3/library/pdb.html).
