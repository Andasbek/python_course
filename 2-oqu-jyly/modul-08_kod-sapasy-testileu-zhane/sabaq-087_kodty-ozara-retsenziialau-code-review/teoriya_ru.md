## 1. Что такое code review

**Code review (рецензирование кода)** — процесс, при котором код, написанный одним программистом, перед добавлением в основной проект читают, проверяют и комментируют другие программисты.

**Что даёт:**

| Польза | Объяснение |
|---|---|
| Раннее обнаружение ошибок | Четыре глаза видят лучше двух; ошибка исправляется до того, как дойдёт до пользователя |
| Качество кода | Единый стиль, понятные имена, простые решения |
| Обмен знаниями | Рецензент узнаёт новый подход, автор получает совет |
| Общая ответственность | Код становится не «моим», а «нашим» |
| Безопасность | Обнаруживаются секреты, SQL-инъекции, непроверенный ввод |

**Роли:**
- **Автор** — тот, кто написал код; объясняет изменение, отвечает на отзывы, исправляет.
- **Рецензент** — читает код, задаёт вопросы, пишет предложения и в конце выносит решение: «одобряю» или «нужны изменения».

## 2. Что проверяем: чек-лист

По степени важности — сначала крупные проблемы, затем мелкие:

| № | Область | Вопросы |
|---|---|---|
| 1 | **Правильность** | Выполняет ли код задачу? Обработаны ли граничные случаи (пустой список, 0, отрицательное число, отсутствующий файл)? |
| 2 | **Безопасность** | Нет ли в коде секретов? Параметризован ли SQL? Проверяется ли ввод? |
| 3 | **Структура** | Короткие ли функции (≈ не более 20–30 строк)? Одна функция — одна задача? Нет ли повторяющегося кода (copy-paste)? |
| 4 | **Читаемость** | Осмысленные ли имена (не `x1`, `data2`)? Есть ли комментарии в сложных местах? |
| 5 | **Стиль (PEP 8)** | Отступ 4 пробела, длина строки ≤ 79–99, пустые строки, `snake_case` |
| 6 | **Тесты** | Есть ли тесты для основных функций? Проходят ли они? |
| 7 | **Документация** | Обновлены ли docstring, README? |
| 8 | **Эффективность** | Нет ли лишних повторений, повторного открытия файла внутри цикла? |

**Правило:** за один подход проверять не более 200–400 строк — внимание снижается. Один review — 30–60 минут.

## 3. Автоматические проверки

Пусть стилистические мелочи находит не человек, а **инструмент** — тогда рецензент сосредоточится на важном.

```bash
pip install flake8
flake8 main.py
```

Результат (пример):
```text
main.py:3:1: F401 'os' imported but unused
main.py:7:80: E501 line too long (94 > 79 characters)
main.py:12:5: E225 missing whitespace around operator
main.py:20:1: E302 expected 2 blank lines, found 1
```

Каждая строка: файл, номер строки, столбец, код ошибки и описание. Другие инструменты: `pylint` (более глубокий анализ, оценка по 10-балльной шкале), `black` (автоматически форматирует код: `black main.py`). В VS Code расширение Python подчёркивает такие предупреждения прямо в коде.

## 4. Пример: разбираем код вместе

```python
import os
def calc(l):
    s=0
    for i in range(len(l)):
        s=s+l[i]
    a=s/len(l)
    if a>=85:
        return "5"
    elif a>=65 and a<85:
        return "4"
    elif a>=40 and a<65:
        return "3"
    else:
        return "2"
print(calc([90,80,70]))
```

**Отзывы рецензента:**

| Строка | Тип | Отзыв |
|---|---|---|
| 1 | Предложение | `import os` не используется — можно убрать. |
| 2 | Предложение | Имена `calc` и `l` не говорят, что делает функция. Например: `ortasha_baga(ballar)`. К тому же маленькая буква `l` похожа на цифру `1` (PEP 8). |
| 3–6 | Предложение | Вместо цикла `sum(ballar) / len(ballar)` — короче и понятнее. |
| 6 | **Обязательно** | При пустом списке — `ZeroDivisionError`. Как правильнее обработать: вернуть 0 или `ValueError`? |
| 9, 11 | Предложение | Условие `a < 85` лишнее — до этой строки доходим только тогда, когда `a < 85`. |
| 8–14 | Вопрос | Возвращать оценку текстом (`"5"`) — это намеренно? Если числом (`5`), потом легче посчитать среднее. |
| — | Обязательно | Нет docstring и тестов. Добавь, пожалуйста, тесты для граничных значений 85, 65, 40. |
| — | Похвала | Логика верная, границы оценок соответствуют заданию — хорошо! |

**Исправленная версия:**

```python
def ortasha_baga(ballar):
    """Переводит средний балл в оценку по 5-балльной шкале.

    Для пустого списка выбрасывает ValueError.
    """
    if not ballar:
        raise ValueError("Список баллов пуст")
    ortasha = sum(ballar) / len(ballar)
    if ortasha >= 85:
        return 5
    if ortasha >= 65:
        return 4
    if ortasha >= 40:
        return 3
    return 2


print(ortasha_baga([90, 80, 70]))
```

Результат:
```text
4
```

## 5. Культура обратной связи

### Правила хорошего отзыва

1. **О коде, а не о человеке.** Не «Ты неаккуратный» → «В этой функции разные отступы».
2. **Конкретно.** Номер строки, пример, почему это важно. Не «Непонятно» → «Имя `process()` не говорит, что обрабатывается, лучше `oqushylardy_suzu()`».
3. **С предложением.** Не только проблема, но и возможное решение.
4. **В форме вопроса.** «Может ли здесь прийти `None`?» — мягче приказа, и автор задумается сам.
5. **Указание важности.** Перед каждым отзывом:
   - **[Обязательно]** — ошибка, безопасность, невыполнение требования; без исправления не одобряется;
   - **[Предложение]** — можно улучшить, но решает автор;
   - **[Вопрос]** — место, которое я не понял;
   - **[Похвала]** — отметить хорошее решение (это тоже важно!).
6. **«Сэндвич»**: сильная сторона → что можно улучшить → пожелание.
7. **Не уделять слишком много внимания мелочам** — стиль пусть находит `flake8`.

| Плохой отзыв | Хороший отзыв |
|---|---|
| «Ошибка.» | «[Обязательно] Строка 24: если `ballar` пуст, будет деление на 0. Может, добавишь проверку `if not ballar:`?» |
| «Имена плохие.» | «[Предложение] Если вместо `d` назвать `oqushy_sozdigi`, будет понятно и через 3 месяца.» |
| «Я бы написал по-другому.» | «[Вопрос] Ты не рассматривал здесь `groupby` вместо `for`? Может получиться короче.» |
| (только критика) | «[Похвала] Функция очистки написана очень чисто, docstring полный — можно брать за образец!» |

### Принятие отзыва

- Отзыв — о **коде**, а не о вас. Каждый отзыв — бесплатный урок.
- Не поняли — уточните: «Можешь показать пример?»
- Не согласны — ответьте с аргументами: «Здесь я вернул 0, а не `ValueError`, потому что в GUI не должно появляться окно ошибки». Решение — совместное.
- Отвечайте на каждый отзыв: «Исправил», «Согласен, в следующем коммите», «Это намеренно, потому что ...».
- Поблагодарите рецензента.

## 6. Code review на GitHub: Pull Request

**Pull Request (PR)** — запрос «Проверьте, пожалуйста, мои изменения и добавьте их в основную ветку».

```text
 main ─────●──────────────────────●────►   (после одобрения — слияние, merge)
            \                    /
 feature     ●───●───●──(PR)───●          (изменения в новой ветке, review, исправления)
```

**Шаги:**

```bash
git checkout -b feature/zhenildik      # 1. новая ветка
# ... изменяем код ...
git add .
git commit -m "Добавлена функция расчёта скидки"
git push -u origin feature/zhenildik   # 2. загрузить ветку на GitHub
```

3. На GitHub кнопка **«Compare & pull request»** → написать заголовок и описание PR (что изменилось, как можно проверить).
4. В разделе **Reviewers** выбрать рецензента (своего напарника). (Рецензент должен быть Collaborator в репозитории: Settings → Collaborators.)
5. Рецензент на вкладке **Files changed** нажимает знак **«+»** рядом со строкой и пишет комментарий. Можно выделить несколько строк и оставить **Suggestion** (готовое предложение исправления).
6. В конце **Review changes** → «Comment» (просто отзыв), «Approve» (одобряю) или «Request changes» (нужны изменения).
7. Автор исправляет и делает `push` нового коммита в ту же ветку — PR обновляется автоматически.
8. После одобрения — **Merge pull request**.

### Парная проверка и парное программирование

- **Парная проверка** — два разработчика по очереди проверяют код друг друга: каждый выступает то автором, то рецензентом.
- **Парное программирование** (pair programming) — двое пишут вместе за одним компьютером: **«водитель»** (driver) печатает, **«штурман»** (navigator) сидит рядом, сразу проверяет код и обдумывает следующий шаг. Каждые 15–20 минут роли меняются. Это code review «в реальном времени».

## Частые ошибки

**1. Одобрение за минуту со словами «всё хорошо».** Для настоящего review запустите код и проверьте хотя бы один граничный случай.

**2. Внимание только к стилю.** 15 отзывов о пробелах, а ошибка деления на 0 не замечена. Сначала правильность и безопасность.

**3. Слишком большой PR.** Изменение на 2000 строк никто внимательно не проверит. Делайте небольшие PR с одной целью.

**4. Обида на отзыв или отсутствие ответа.** Ответ на каждый отзыв — профессиональная культура.

**5. Навязывание рецензентом своего стиля.** «Я бы написал по-другому» — не аргумент. Нужно указать правило (PEP 8, задание, безопасность) или конкретную пользу.

## Основные понятия

| Понятие | Объяснение |
|---|---|
| Code review | Проверка кода другим программистом и отзыв о нём |
| Автор / рецензент | Тот, кто написал / проверяет код |
| Конструктивный отзыв | Конкретный, вежливый отзыв с предложением |
| Pull Request (PR) | Запрос на проверку и слияние изменений из ветки |
| Approve / Request changes | Одобрить / потребовать изменений |
| Merge | Слияние ветки с основной веткой |
| Линтер (`flake8`, `pylint`) | Инструмент автоматической проверки стиля и возможных ошибок |
| Парное программирование | Совместное написание одного кода двумя людьми (водитель + штурман) |

## Примечание

- Коды `flake8` имеют префиксы: `E`/`W` — нарушения стиля PEP 8 (pycodestyle), `F` — логические проблемы (pyflakes: неиспользуемый импорт, неопределённое имя), `C9` — сложность функции.
- Настройки линтера хранят в файле проекта (`setup.cfg`, `.flake8` или `pyproject.toml`), например `max-line-length = 99`, чтобы у всех участников были одинаковые правила.
- `black` по умолчанию использует длину строки 88 символов; чтобы `flake8` не спорил с ним, увеличьте `max-line-length` до 88 и добавьте `extend-ignore = E203`.
- Современная альтернатива — `ruff`: один быстрый инструмент, объединяющий проверки `flake8`, `isort` и форматирование (`ruff check`, `ruff format`).
- Сам PEP 8 допускает отступления ради читаемости («A Foolish Consistency is the Hobgoblin of Little Minds»); согласованность внутри проекта важнее буквального следования правилу.
- Документация: [PEP 8](https://peps.python.org/pep-0008/), [GitHub: About pull request reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews).
