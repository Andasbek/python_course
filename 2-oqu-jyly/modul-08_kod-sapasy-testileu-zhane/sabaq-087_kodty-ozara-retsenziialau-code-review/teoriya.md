# Сабақ 87. Кодты өзара рецензиялау (code review). Жұптық тексеру және пікір беру.

## Тақырыптар

1. Code review деген не
2. Не тексереміз: чек-парақ
3. Автоматты тексерулер
4. Мысал: кодты бірге талдау
5. Пікір беру мәдениеті
6. GitHub-тағы code review: Pull Request

## 1. Code review деген не

**Code review (кодты рецензиялау)** — бір бағдарламашы жазған кодты басқа бағдарламашы(лар) негізгі жобаға қосылмас бұрын оқып, тексеріп, пікір беру үдерісі.

**Не береді:**

| Пайда | Түсіндірме |
|---|---|
| Қателерді ерте табу | Төрт көз екі көзден жақсы көреді; қате пайдаланушыға жетпей тұрып түзетіледі |
| Код сапасы | Бірыңғай стиль, түсінікті атаулар, қарапайым шешімдер |
| Білім алмасу | Рецензент жаңа тәсіл үйренеді, автор кеңес алады |
| Ортақ жауапкершілік | Код «менікі» емес, «біздікі» болады |
| Қауіпсіздік | Құпиялар, SQL инъекциясы, тексерілмеген енгізу табылады |

**Рөлдер:**
- **Автор** — кодты жазған адам; өзгерісті түсіндіреді, пікірлерге жауап береді, түзетеді.
- **Рецензент** — кодты оқып, сұрақ қояды, ұсыныс жазады, соңында «бекітемін» немесе «өзгерту керек» деп шешім айтады.

## 2. Не тексереміз: чек-парақ

Маңыздылық ретімен — алдымен үлкен мәселелер, сосын ұсақтары:

| № | Сала | Сұрақтар |
|---|---|---|
| 1 | **Дұрыстық** | Код тапсырманы орындай ма? Шекаралық жағдайлар (бос тізім, 0, теріс сан, жоқ файл) өңделген бе? |
| 2 | **Қауіпсіздік** | Кодта құпия жоқ па? SQL параметрлі ме? Енгізу тексеріле ме? |
| 3 | **Құрылым** | Функциялар қысқа ма (≈ 20–30 жолдан аспайды)? Бір функция — бір міндет пе? Қайталанатын код (copy-paste) жоқ па? |
| 4 | **Оқылымдылық** | Атаулар мағыналы ма (`x1`, `data2` емес)? Күрделі жерлерде түсініктеме бар ма? |
| 5 | **Стиль (PEP 8)** | Шегініс 4 бос орын, жол ұзындығы ≤ 79–99, бос жолдар, `snake_case` |
| 6 | **Тесттер** | Негізгі функцияларға тест бар ма? Олар өте ме? |
| 7 | **Құжаттама** | Docstring, README жаңартылған ба? |
| 8 | **Тиімділік** | Қажетсіз қайталау, циклдің ішінде файлды қайта ашу жоқ па? |

**Ереже:** бір отырыста 200–400 жолдан артық тексермеу — зейін төмендейді. Бір review — 30–60 минут.

## 3. Автоматты тексерулер

Стильдік ұсақ-түйекті адам емес, **құрал** тапсын — сонда рецензент маңызды нәрсеге назар аударады.

```bash
pip install flake8
flake8 main.py
```

Нәтижесі (мысал):
```text
main.py:3:1: F401 'os' imported but unused
main.py:7:80: E501 line too long (94 > 79 characters)
main.py:12:5: E225 missing whitespace around operator
main.py:20:1: E302 expected 2 blank lines, found 1
```

Әр жол: файл, жол нөмірі, баған, қате коды және сипаттамасы. Басқа құралдар: `pylint` (тереңірек талдау, 10 балдық баға), `black` (кодты автоматты пішімдейді: `black main.py`). VS Code-та Python кеңейтімі мұндай ескертулерді код астына сызып көрсетеді.

## 4. Мысал: кодты бірге талдау

```python
import os
def calc(l):
    s=0
    for i in range(len(l)):
        s=s+l[i]
    a=s/len(l)
    if a>=85:
        return "5"
    elif a>=65 and a<85:
        return "4"
    elif a>=40 and a<65:
        return "3"
    else:
        return "2"
print(calc([90,80,70]))
```

**Рецензенттің пікірлері:**

| Жол | Түрі | Пікір |
|---|---|---|
| 1 | Ұсыныс | `import os` қолданылмайды — алып тастауға болады. |
| 2 | Ұсыныс | `calc` және `l` атаулары не істейтінін айтпайды. Мысалы: `ortasha_baga(ballar)`. Сондай-ақ кіші `l` әрпі `1` цифрына ұқсайды (PEP 8). |
| 3–6 | Ұсыныс | Циклдің орнына `sum(ballar) / len(ballar)` қысқа әрі түсінікті. |
| 6 | **Міндетті** | Бос тізім берілсе — `ZeroDivisionError`. Қалай өңдегенің дұрыс: 0 қайтару ма, әлде `ValueError`? |
| 9, 11 | Ұсыныс | `a < 85` шарты артық — бұл жолға тек `a < 85` болғанда жетеміз. |
| 8–14 | Сұрақ | Бағаны мәтін (`"5"`) етіп қайтару әдейі ме? Сан (`5`) болса, кейін орташасын есептеу оңай. |
| — | Міндетті | Docstring және тест жоқ. Шекаралық 85, 65, 40 мәндеріне тест қосшы. |
| — | Мақтау | Логика дұрыс, баға шекаралары тапсырмаға сай — жақсы! |

**Түзетілген нұсқасы:**

```python
def ortasha_baga(ballar):
    """Баллдардың орташасын 5 балдық бағаға аударады.

    Бос тізім үшін ValueError шығарады.
    """
    if not ballar:
        raise ValueError("Баллдар тізімі бос")
    ortasha = sum(ballar) / len(ballar)
    if ortasha >= 85:
        return 5
    if ortasha >= 65:
        return 4
    if ortasha >= 40:
        return 3
    return 2


print(ortasha_baga([90, 80, 70]))
```

Нәтижесі:
```text
4
```

## 5. Пікір беру мәдениеті

### Жақсы пікірдің ережелері

1. **Кодқа, адамға емес.** «Сен ұқыпсызсың» емес → «Бұл функцияда шегініс әртүрлі».
2. **Нақты.** Жол нөмірі, мысал, неге маңызды екені. «Түсініксіз» емес → «`process()` атауы не өңдейтінін айтпайды, `oqushylardy_suzu()` жақсырақ».
3. **Ұсыныспен.** Тек мәселе емес, мүмкін шешім де.
4. **Сұрақ түрінде.** «Мұнда `None` келуі мүмкін бе?» — бұйрықтан жұмсақ әрі автор өзі ойланады.
5. **Маңыздылығын белгілеу.** Әр пікірдің алдына:
   - **[Міндетті]** — қате, қауіпсіздік, талаптың орындалмауы; түзетілмесе бекітілмейді;
   - **[Ұсыныс]** — жақсартуға болады, бірақ автор өзі шешеді;
   - **[Сұрақ]** — түсінбеген жерім;
   - **[Мақтау]** — жақсы шешімді атап өту (бұл да маңызды!).
6. **«Сэндвич»**: жақсы жағы → жақсартуға болатыны → тілек.
7. **Ұсақ-түйекке тым көп көңіл бөлмеу** — стильді `flake8` тапсын.

| Нашар пікір | Жақсы пікір |
|---|---|
| «Қате.» | «[Міндетті] 24-жол: `ballar` бос болса, 0-ге бөлу болады. `if not ballar:` тексерісін қоссаң қалай?» |
| «Атаулар жаман.» | «[Ұсыныс] `d` орнына `oqushy_sozdigi` деп атасаң, 3 айдан кейін де түсінікті болады.» |
| «Мен басқаша жазар едім.» | «[Сұрақ] Мұнда `for` орнына `groupby` қолдануды қарастырдың ба? Қысқарақ болуы мүмкін.» |
| (тек сын) | «[Мақтау] Тазалау функциясы өте таза жазылған, docstring толық — үлгі алатындай!» |

### Пікірді қабылдау

- Пікір — **кодқа**, сізге емес. Әрбір пікір — тегін сабақ.
- Түсінбесеңіз — нақтылаңыз: «Мысал көрсете аласың ба?»
- Келіспесеңіз — дәлелмен жауап беріңіз: «Мұнда `ValueError` емес, 0 қайтардым, себебі GUI-де қате терезесі шықпауы керек». Шешім — бірлесіп.
- Әр пікірге жауап беріңіз: «Түзеттім», «Келісемін, келесі коммитте», «Бұл әдейі, себебі ...».
- Рецензентке алғыс айтыңыз.

## 6. GitHub-тағы code review: Pull Request

**Pull Request (PR)** — «Менің өзгерістерімді тексеріп, негізгі тармаққа қосыңыздаршы» деген сұраныс.

```text
 main ─────●──────────────────────●────►   (бекітілгеннен кейін біріктіру — merge)
            \                    /
 feature     ●───●───●──(PR)───●          (жаңа тармақтағы өзгерістер, review, түзетулер)
```

**Қадамдары:**

```bash
git checkout -b feature/zhenildik      # 1. жаңа тармақ
# ... кодты өзгерту ...
git add .
git commit -m "Жеңілдік есептеу функциясы қосылды"
git push -u origin feature/zhenildik   # 2. тармақты GitHub-қа жүктеу
```

3. GitHub-та **«Compare & pull request»** батырмасы → PR тақырыбы мен сипаттамасын жазу (не өзгерді, қалай тексеруге болады).
4. **Reviewers** бөлімінде рецензентті (жұбыңызды) таңдау. (Рецензент репозиторийде Collaborator болуы керек: Settings → Collaborators.)
5. Рецензент **Files changed** қойындысында жолдың жанындағы **«+»** белгісін басып, түсініктеме жазады. Бірнеше жолды белгілеп, **Suggestion** (дайын түзету ұсынысы) қалдыруға болады.
6. Соңында **Review changes** → «Comment» (жай пікір), «Approve» (бекітемін) немесе «Request changes» (өзгерту керек).
7. Автор түзетіп, жаңа коммитті сол тармаққа `push` жасайды — PR автоматты жаңарады.
8. Бекітілгеннен кейін — **Merge pull request**.

### Жұптық тексеру және жұптық бағдарламалау

- **Жұптық тексеру** — екі әзірлеуші бір-бірінің кодын кезекпен тексереді: әрқайсысы бірде автор, бірде рецензент болады.
- **Жұптық бағдарламалау** (pair programming) — бір компьютерде екеуі бірге жазады: **«жүргізуші»** (driver) пернетақтада жазады, **«штурман»** (navigator) қатар отырып, кодты бірден тексереді, келесі қадамды ойлайды. 15–20 минут сайын рөл ауысады. Бұл — «нақты уақыттағы» code review.

## Жиі кездесетін қателер

**1. «Бәрі жақсы» деп бір минутта бекіту.** Шын review үшін кодты іске қосып, кемінде шекаралық бір жағдайды тексеріп көріңіз.

**2. Тек стильге назар аудару.** 15 пікір бос орындар туралы, ал 0-ге бөлу қатесі байқалмаған. Алдымен дұрыстық пен қауіпсіздік.

**3. Тым үлкен PR.** 2000 жолдық өзгерісті ешкім мұқият тексермейді. Шағын, бір мақсатты PR жасаңыз.

**4. Пікірге ренжу немесе жауапсыз қалдыру.** Әр пікірге жауап — кәсіби мәдениет.

**5. Рецензенттің өз стилін таңуы.** «Мен басқаша жазар едім» — дәлел емес. Ереже (PEP 8, тапсырма, қауіпсіздік) немесе нақты пайда көрсетілуі керек.

## Негізгі ұғымдар

| Ұғым | Түсіндірме |
|---|---|
| Code review | Кодты басқа бағдарламашының тексеруі және пікір беруі |
| Автор / рецензент | Кодты жазған / тексеретін адам |
| Сындарлы пікір | Нақты, сыпайы, ұсынысы бар пікір |
| Pull Request (PR) | Тармақтағы өзгерістерді тексеруге және біріктіруге сұраныс |
| Approve / Request changes | Бекіту / өзгертуді талап ету |
| Merge | Тармақты негізгі тармаққа біріктіру |
| Линтер (`flake8`, `pylint`) | Стиль мен ықтимал қателерді автоматты тексеретін құрал |
| Жұптық бағдарламалау | Екі адамның бір кодты бірге жазуы (жүргізуші + штурман) |

## Ескерту

- `flake8` кодтарының префикстері бар: `E`/`W` — PEP 8 стилін бұзу (pycodestyle), `F` — логикалық мәселелер (pyflakes: қолданылмаған импорт, анықталмаған атау), `C9` — функцияның күрделілігі.
- Барлық қатысушыда ережелер бірдей болуы үшін линтер баптаулары жоба файлында сақталады (`setup.cfg`, `.flake8` немесе `pyproject.toml`), мысалы `max-line-length = 99`.
- `black` әдепкі бойынша 88 таңбалық жол ұзындығын қолданады; `flake8` онымен қайшыласпауы үшін `max-line-length` мәнін 88-ге дейін көбейтіп, `extend-ignore = E203` қосыңыз.
- Заманауи балама — `ruff`: `flake8`, `isort` тексерулері мен пішімдеуді біріктіретін бір жылдам құрал (`ruff check`, `ruff format`).
- PEP 8 өзі оқылымдылық үшін ауытқуларға жол береді («A Foolish Consistency is the Hobgoblin of Little Minds»); жоба ішіндегі біркелкілік ережені сөзбе-сөз орындаудан маңыздырақ.
- Құжаттама: [PEP 8](https://peps.python.org/pep-0008/), [GitHub: About pull request reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews).
